### What changed

- **`check-repo.js defects`** checks that each entry's test exists by file and method name (a NOTE when not) and fails only a test the document names that carries more than a one-line `/// <summary>` or a `<remarks>` block. The `Test:` line placement check (a failure since 2026-10-07) and its blank-line WARN are gone; the document's sections, order, counts, `**Fix:**`/`**Test to flip:**` lines, "Found without a test" shape and `// Same case as` comments are NOTE lines.
- **`check-repo.js gates`**: the gates the 2026-10-09 version inventoried for the first time, or covered only with credits it refused, are `GATE missing:` lines now; each says it was provisional in 2026-10-09. - **`check-repo.js tests`**: the dynamic-skip, prose and empty-grant WARNs are NOTE lines for the reviewer.
- **`check-repo.js removed`** accounts itself for a method moved to another class with an identical body, a method renamed in its class with an identical body, theory rows merged into an identical theory, and rows kept with an argument added; writes them to `<app>.removed-tests-matched.md` when run without `--base` (`--no-write` prints only); reads one notation (`-> D -> <reason>`; E names the deleted production file); fails every removal without a valid line; `--d-lines` prints the D line behind each dropped test. Its summary now also gives the tree's test count, the added count and the per-letter tally.
- **`verify.sh`** writes the verify log (`--log-dir`), fails the removed-tests check, prints NOTE lines and counts them, and runs `removed` with `--no-write`.
- **Docs:** `SETUP.md` (setup mode, from the archived writer text, each step with its done-when); WORKFLOW.md reduced to the stack's own (suites, the work-list commands, what `verify.sh` checks, break-gate on an API, delivery of an API); README file table and "Defect documents"; CONVENTIONS section 2 (the accounting points at the shared notation), section 3 (the format points at the shared one; what stays is the API's: the one-line summary, a characterized 500's `Detail`, consumers of a cross-repo fix, `// Same case as`, the shape-test vehicle, recurring patterns over a route table, the recurring defects), section 4 (provisional gates, allow-list NOTEs), section 5 (`break-gate.sh`), section 6 (a credit that does not hold is a blocker).

## 2026-10-09 — the gates check credits per call site; a removed-tests guard; HubHarness addressing helpers

Consumes every item of `agent-docs/api-testing-proposals-2026-10-07.md` (with its 2026-10-08 and 2026-10-09 additions and the item recovered from `.claude/agents`); each carries its disposition there. Two shared C# files changed, additively (`HubHarness.cs`, `ApiTestBase.cs`); `check-repo.js`, `verify.sh`, README, CONVENTIONS, WORKFLOW, `agent-docs/api-test-gaps/README.md` and the `dotnet-test-writer` and `api-test-reviewer` agent files changed. **Start a new session** before launching either agent. Nothing new fails a pushed branch this round: every new check prints `WARN` lines, and the next standard change turns them into failures (see "Breaking, next round").

### What changed

**`check-repo.js gates`: credits per call site.**
- *Branch gates per site.* A site's verdict can decide a refusal (an `if` that throws or forbids, a handler's `Authorize`, a returned verdict), pick a branch (passed to a call, read in an `if` that refuses nobody, combined into a flag), or both. A member that throws elsewhere no longer hides a branch site: cite.api's `ScoringCategoryController.GetForScoringModel:1` (`viewAsAdmin`, in the refusal and passed to the service) is credited with its other-branch tests. A site that only picks a branch takes no 403 as its near miss (the 403 comes from another gate); its other branch is a granted 2xx caller holding none of its permissions (nor those of the sites its verdict is combined with), a test named for what the branch leaves out where the site names no permission, or a service or hub test refused without a status.
- *Allowed case.* Never a case answering 5xx. Not a case holding a permission of an earlier site that short-circuits this one (`!a && !b`, `a || b`, `else if`, a flag both feed, two verdicts handed to one call); `!a || !b` and sequential refusals need both. Not an actor holding every system permission that all the case's requests use.
- *Near miss.* Not `Root`, not a scope test, not a seeded id read as a grant (`TestData.Permissions.CreateViews`). A route denial counts only if the caller passes every earlier refusing gate on that route (the controller's own check before the service's, the handler's `Authorize` before `HandleRequest`, an earlier refusing site that must also admit). In a short-circuit chain it holds a permission of the site's family, so each tier has its own near miss. A site inside a loop takes only a test that names it with `// Gate:`. A `_does_not_let_a_caller_` test that asserts admission, and a Leave method's test by what it does not join, are no denials.
- *Credits shown.* `--covered` prefers a test no defect entry names, linked by route, from the gate's own class, holding the fewest permissions (and a near miss of the site's family); lists one allowed case per accepted permission; prints `tiers: system <case>, resource <case>` for a two-tier site.
- *Allow-list precedence.* A reason starting `Inert:`, or naming an entry or "Needs a decision" item of the defect document by its test name, stands even where tests are credited: `ALLOWED`, counted as allow-listed, with a `LISTED` line under `--covered`. `Defect:` naming no entry warns. Other listed gates the check covers still warn "covered now".
- *Inventory.* A class's own `Can*` helper that asks the authorization service, called without a receiver (vm.api's `VmService.CanViewMapAsync`, `CanManageMapsForTeamsAsync`, `NetworkService.CanViewNetworks`, caster.api's `FileCommandHandler.CanLock`); the sub-gates inside cite.api's selector helper `SubmissionService.HasSpecificPermission`, reached by the call sites passing a `SpecificPermission` value that leads to them; the default policy's and the MVC `AuthorizeFilter`'s scope requirement (`#<Type>.<Member>[scope]`); hubs from `MapHub<T>` (the class's `[Authorize]`, or `.RequireAuthorization()` on the mapping as `#<Hub>[RequireAuthorization]`), so vm.api's unmapped `Hubs/VmHub.cs` is `NOTE unrouted` and its two mapped hubs are gates. Types resolve by namespace (vm.api's two `BaseHandler`s). Parameters are read from the signature: an attribute `[ProducesResponseType(typeof(IEnumerable<SystemPermission>))]` had made every member named `GetMine` look like gate machinery, which hid blueprint.api's `MselController.GetMine`. `NOTE uninventoried` lists members that throw `ForbiddenException` with no call the check inventories (data and claims gates, for the reviewer).
- *Linking.* Urls built by concatenation or `.Replace(...)`, helpers and properties whose body holds one route literal (82 more blueprint.api cases resolve, 22 vm.api, 12 player.api); a case with an unresolved request is linked by name too; an `HttpClient`-named call (`GetAsync`) links by name only off a client.
- *Provisional.* A newly inventoried gate, or one covered only by a credit this version refuses, prints `WARN provisional: <id> ... (<why>)` and counts in the summary, now `(gates: N call sites in M members, C covered, A allow-listed, X missing, P provisional)`, never as missing.
- `--app <app>` and `--app=` are accepted; a `.csproj` argument may be absolute.

**`check-repo.js removed <repo> [<app>] [<test.csproj>] [--base <ref>] [--strict]`, new, run by `verify.sh` (step 1e) as warnings.** It compares the tree with the merge base of `origin/main` (`--base` picks another ref): every `[Fact]`/`[Theory]` method, and every `[InlineData]` row of a theory that stays, that the base had and the tree has not (a method in its renamed file, or the same class and method anywhere, has moved). Each must have a line in `agent-docs/api-test-bugs/<app>.removed-tests-<date>.md`: ``- `Old` -> A|B|C|E -> `New` `` naming a test that exists, or ``- `Old` -> D <reason> `` whose reason is not budget, time, "trivial" or a follow-up. `REMOVED` lines name each gap; `--strict` fails them.

**`check-repo.js tests` and `defects`: three new WARN lines.** A dynamic skip (`Assert.Skip`/`SkipWhen`/`SkipUnless`); prose that reads like a defect note (`turns ... red`, `makes ... green`: the four hits today are not defect notes, which is why it warns); a `Test:` line on the blank line, brace or signature beside its assertion. The existing failures are unchanged: `harness`, `tests` and `defects` print byte-identical output to the previous script on all eight worktrees, apart from these WARN lines.

**`HubHarness` (shared, additive).** `Addressed`, every audience of `Clients` the hub read, in order; `AssertAddressedOnly(params string[] members)`; `NothingAddressed()`. Both also fail when the hub read `Context.Features` or aborted the connection. Promoted from blueprint.api's `AssertAddressedOnlyOthersInGroup`.

**`ApiTestBase<TContext>` (shared, additive).** `SessionId`, the `X-Test-Session` value every client it builds sends, for a request or hub connection a test builds by hand. All eight suites read it today as `Client().DefaultRequestHeaders.GetValues(TestDatabaseScope.HeaderName)`.

**Conventions.**
- Section 1. One Act: a read-only precondition through the database is arrange; two side-effect-free requests compared are one Act; a precondition through a request, a preview then the import it predicts, and two callers sending the same request are second tests (README's guidance row says how this differs from "Avoid multiple Act tasks"). Hub tests: vm.api's mapped hubs are gated by `MapHub<T>().RequireAuthorization()` under the default policy, not a Bearer attribute; real-connection tests do not exercise the `access_token` promotion; the SignalR client pin in a CPM repo is a `Directory.Packages.props` line; hub method tests end with `AssertAddressedOnly(...)` or `NothingAddressed()`. Dynamic skips are inventoried; a skip true in every run is dead code. Option A doubles answer every route production calls.
- Section 2, new "Removing or replacing a test": the narrowing rule (every observable, assertions inside fake handlers and stubs included, every theory row); the accounting form with A, B, C, D and E (E for a path a surviving test already covers, not a licence to collapse cases); the `removed` check; thresholds and counts only ratchet up.
- Section 3. One `///` line is the one-line summary. A characterized 500's `Detail` under Production hosting has no stack frame: assert the message, plus the state the throw left where that tells throws apart; a service-level defect test asserts the type and the message or `ParamName`. The resource-membership escalation shares the self-promotion entry shape; reachability is judged against the shipped roles and documented endpoints, otherwise `(latent: unreachable input)`.
- Section 4. The near miss asserts the gate's own refusal where another step answers the same status; two-tier gates whose second tier covers a subset need a near miss on it; bypass gates; scope tests per configured scope and mapping family, with a string-only scope table theory allowed; the gates-check bullets rewritten for all of the above; allow-list reason kinds (an allowed case only a defect shows, an inert verdict) and `Inert:`/`Defect:`.
- Section 5. Forms for an inverted gate (`if (false && await X)`), a mapping-gated hub (`.AllowAnonymous()`), and the doubled scope requirement (policy and filter).
- Section 6. An allow-list reason the harness can meet is a blocker ("not finished"); one that misdescribes a covered gate is a should-fix; provisional lines are untested gates for the verdict.
- WORKFLOW. Step B.2 reads the writer's "Removed tests" and "Permission coverage" first and returns a diff with unaccounted removals before review; B.3 names the accounting file; B.5 "ready" needs no provisional gate, a clean removed-tests check and permission coverage; C quotes the removed-tests summary, A to E totals and D lines; process defects found after "ready" go back into the agent definition or check the same day.

## 2026-10-07 — the gates check: an untested authorization gate is a blocker

### What changed

**`check-repo.js gates`, run by `verify.sh` as a FAIL (step 1d).** It inventories every authorization call site in the application and fails each one without an allowed case that is not `Root` and a near-miss denied case. CONVENTIONS.md section 4, "The gates check", says exactly what it recognizes; in short:
- Gates: service calls of `Authorize`/`Authorize<T>`/`AuthorizeAsync`/`HasSpecificPermission`/`Can`/`Can*`, requirements' `IsMet`, calls to app helpers that take permission arrays, in controller actions, MediatR handlers (`Authorize` overrides, `Handle`), services (cite.api's `var hasPermission = ...`), hub methods and private helpers (credited to their callers); plus one gate per hub carrying `[Authorize]` (its real connection). Authorization machinery (`Authorization/` folders, authorization services, requirements, handlers, claims services, AutoMapper resolvers) is not a gate. `NOTE` lines list `[AllowAnonymous]` routes, handlers whose `Authorize` returns `true`, and unrouted (latent) gates.
- Tests reach a gate by their request (verb and url from literals, interpolations, constants, theory rows, `[MemberData]` string tables, helpers, matched to controller `[Route]`/`[Http*]`, minimal-API `Map*` under `MapGroup`, and the actions that send a request or call a service; most specific route wins), by name when they send none (class stem plus leading operation word, or a call to the member), or by `// Gate: <id>`.
- Allowed: a non-denial, non-Root, non-anonymous case holding one of the call site's permissions (or the role or membership that carries it where `TestActor` cannot name it). Near miss: a denial (per request, so a control request is not read as denied) whose caller holds a grant or carries `// Data-row gate:`. Branch gates (a filter, refusing nobody) take a granted caller without the permission instead.
- Allow-list `/mnt/data/crucible/agent-docs/api-test-gaps/<app>.txt` (one per app, outside every repo like the defect documents; the folder's README says what the files are), `<gate id> Reason: <why>`, for what the harness genuinely cannot reach. The check finds it by the app name (`check-repo.js gates <repo> [<app>]`; `verify.sh` passes `--app`), reads no other list, and fails a test project holding an `untested-gates.txt`, so none is committed by habit. A missing reason, a reason about budget, time, a follow-up, a later or next round or scope, and a stale id fail; a listed gate that is now covered warns. `ALLOWED` lines print in every run.
- `--covered` prints the allowed and near-miss tests credited for each covered gate, for the reviewer.

**Writer, reviewer, delivery.**

**Step 1B in the templates** (alloy, caster, cite, gallery and steamfitter had hand-written copies; blueprint and vm per-class variants).

A resolution outside any request gets a context over the session the function returns, while it returns one, and throws as before when it returns null. The five run-wide copies built over the host scope instead.

Every run-wide factory overrides `CreateHost` to build one host under a lock and hand it to every caller (caster.api's form). `WebApplicationFactory.StartServer` takes no lock (checked in the `release/10.0` source), and `CreateClient` in either overload, `CreateDefaultClient`, `Services` and `Server` all pass through `StartServer` to `CreateHost`, so the lock covers them all. A lock around `CreateClient()` alone, one repo's first form, is bypassed by `Factory.Services`, `Factory.Server` and `CreateClient(options)`. 1A deletes `_started`, which would otherwise be CS0414.
- `PerClassAppFactory.template.cs` has the same fallback, with `_started` set in `CreateHost` and no lock (one class's tests run one after another). - README "Known pitfalls" has two new entries: `InitializeDatabase` resolves the context outside a request and publishes entity events; `StartServer` takes no lock.

### Decisions taken from a sibling instead of player.api

- **Lazy container start** (vm.api, blueprint.api). player.api started PostgreSQL in the assembly fixture's `InitializeAsync`, so a machine without Docker failed every test, including the pure unit tests. `PostgresTestDatabase` starts it on the first `BeginSessionAsync`, caches the start (faulted included, so one clear error rather than a timeout per test) and builds the container inside the start rather than in a field initializer (blueprint.api's finding: `Build()` resolves the Docker endpoint, and a throw from a constructor defeats the clear error). On the pilot the provider banner now prints at the first database test rather than before the run; CI's grep is unaffected.
- **Clear only the template's pool after migrating**, not `ClearAllPools()` (vm.api's per-database `ClearPool` idea applied to the template), because with a lazy start other tests' pools may already exist.
- **Testcontainers.PostgreSql 4.15.0** (vm.api, blueprint.api), not player.api's 4.13.0. The pilot was bumped.
- **`RecordingLogger`** (vm.api, blueprint.api) joins the shared files, made concurrent because the code that logs often runs on its own thread.
- **The per-class factory variant** (vm.api, blueprint.api: `IClassFixture` over `Startup` with a host database of its own) is a supported template for apps whose tests assert on NSubstitute doubles the host resolves. player.api's run-wide factory stays the default.
- **A throwaway host database** (blueprint.api) is the run-wide template's step 1B for apps whose `Program.Main` has no switch that skips `InitializeDatabase`; player.api's `open-api-only` gate is step 1A.
- **ReportGenerator** stays optional: vm.api's `scripts/coverage.sh` and tool manifest are allowed extras, not part of the standard (nothing gates on coverage).
- **`coverlet.runsettings` beside the test project**, as player.api has it, rather than at the repository root (vm.api, blueprint.api), because `RunSettingsFilePath` then applies it to every run without a `--settings` argument. Its exclusions use wildcards (`[*.Migrations.PostgreSQL]*`, `[*.Tests]*`, `**/Migrations/**`) so one file fits every app, including those whose migrations live in the API assembly.

### Where the standard departs from player.api's own files

- `TreatWarningsAsErrors` and `WarningsNotAsErrors` move from the root `Directory.Build.props` into a test-project `Directory.Build.props` that imports the repository's own first. Five of the eight APIs have no root `Directory.Build.props`; turning warnings into errors for their application projects is a separate change. NU1510 joins the list (blueprint.api needs it). player.api's root file is unchanged.
- The CI workflow runs `dotnet test <test project dir>` rather than `dotnet test` at the root, so a repository with several solutions or projects at the root runs the one suite. Everything else is player.api's `build-and-test.yml`.
- The banner text is `[<Tests assembly>] database provider: PostgreSQL (postgres:16-alpine, real migrations)` (player.api: `... (real migrations, snake_case casing and store-generated UUIDs are covered)`); the prefix CI greps is unchanged.
- Defect notes leave the code. player.api's docs/Testing.md told tests to describe a defect in `<summary>` and say "Turns red when ..." in `<remarks>`; the user forbids defect commentary in repository code, so a test now carries at most a one-line neutral `<summary>` of the current behaviour and the defect is an entry in `agent-docs/api-test-bugs/<app>.md` (CONVENTIONS.md section 3). The pilot had 61 "Turns red" blocks: 59 that a one-line search finds, and two where the phrase wraps across lines ("Turns" / "red", at `Player.Api.Tests/Features/Applications/ApplicationTemplateRequestTests.cs:77-78` and `Player.Api.Tests/Features/Views/ViewImporterTests.cs:318-319`). The first rewrite cut the 59 to a one-line neutral `<summary>` and moved them into `agent-docs/api-test-bugs/player.api.md`: 50 entries (four pairs of tests share one fix and so one entry), 5 under `## Needs a decision`, and 7 shared recipes. It missed the two wrapped blocks. It also missed about 11 blocks that open "Characterizes current behaviour" without "Turns red" (several say "Flip to" or "goes red" instead), and several `<remarks>` blocks that describe a defect in prose. `check-repo.js tests` passed all of them, because it read one line at a time and knew only "turns red", so defect notes do remain in the pilot's tests. The check changes in the entry above flag them. A few test-body comments that stated the expected behaviour were neutralized; no code, assertion or test name changed.

### Where the standard differs from Microsoft guidance (README, "Microsoft guidance")

- One run-wide `WebApplicationFactory` as an xUnit v3 assembly fixture rather than `IClassFixture` per class; the price is the recorder rule.
- The production database provider (PostgreSQL through Testcontainers) rather than the SQLite in-memory provider the ASP.NET Core integration-test page recommends; this follows the EF Core testing guidance instead.
- A database per test cloned from a migrated template, rather than EF's transaction-per-test isolation, which would discard entity events.
- Test names are snake_case sentences, not `Method_Scenario_Expected`; no Arrange/Act/Assert comments; `[Theory]` only for data-only variation (house style from player.api).
- Integration and unit tests share one project per API (Microsoft suggests separate projects); the base class says which kind a test is.
- VSTest mode of `dotnet test`, not the .NET 10 SDK's Microsoft.Testing.Platform mode, until `xunit.v3` 4.x is stable (coverlet has no MTP collector; Microsoft's MTP coverage extension needs MTP 2.x, which stable xUnit v3 does not support).
