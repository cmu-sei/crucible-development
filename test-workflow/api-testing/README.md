# Crucible API test standard

The canonical xUnit v3 test setup for every Crucible-family .NET API (alloy.api, blueprint.api, caster.api, cite.api, gallery.api, steamfitter.api, player.api, vm.api). It was extracted from player.api's suite and made app-neutral; player.api's [docs/Testing.md](../../player/player.api/docs/Testing.md) remains the worked example of a repo on it. The `dotnet-test-writer` agent copies the shared files into an API repo verbatim and builds the app-specific ones from `templates/`, so the harness reads the same everywhere. **Change the standard here first, then roll it out to the repos**; never edit a shared copy in one repo and leave the others behind. Only the `test-standard-maintainer` agent edits this folder, at a standard version. How tests are written (conventions, priorities, defect entries, review criteria) is in [CONVENTIONS.md](CONVENTIONS.md), the shared source for the writer and the reviewer. Setting a repo up is [SETUP.md](SETUP.md), read in setup mode only. Defects the tests find are described in one document per app, `agent-docs/api-test-bugs/<app>.md`, never in test comments (CONVENTIONS.md section 3). The workflow, the file formats and the scripts both stacks share are in [../testing/README.md](../testing/README.md); what is particular to this stack is in [WORKFLOW.md](WORKFLOW.md); what changed and how to adopt it is in [CHANGELOG.md](CHANGELOG.md). It mirrors the UI standard in [../ui-testing/](../ui-testing/README.md).

`<Tests>` below is the test project's directory (`Player.Api.Tests`, `src/Player.Vm.Api.Tests`, `test/Caster.Api.Tests`, ...). Every repo has exactly one `*.Tests.csproj`.

The shared C# files use one namespace, `Crucible.Api.Testing`, in every repo (the test `.csproj` imports it with `<Using Include="Crucible.Api.Testing" />`), start with `#nullable disable` and carry their own `using` lines, so they compile byte-identical whatever the repo's `Nullable` and `ImplicitUsings` settings. A repo may add helpers the standard has no equivalent for, in `<Tests>/Support/` and named for what they fake (player.api: `WebhookRecorder`, `EndpointHarness`, `ArchiveHelper`; vm.api: `FakeProxmoxCluster`, `FakeChangeFeed`; steamfitter.api: `TaskActionRecorder`), or, for a seed-graph helper, for the graph it builds (cite.api's `TestScenario`; CONVENTIONS.md section 1). `Support/Shared/` holds shared files only. If a second repo needs an extra, promote it into the standard, and the repos' copies go. Two extras share a name without being one extra: player.api's and caster.api's `ArchiveHelper` build different archives for different endpoints, so neither is promoted. A capability only one repo's tests need stays an extra beside the shared type it wraps, not inside it: blueprint.api's concurrency gate (`Yields`, `Holds`, `HoldsUntil`) is a `DelegatingHandler` in front of a `StubHttpMessageHandler`.

## One SDK version per repo

Every Crucible API's `global.json` pins SDK `10.0.100` with `rollForward: latestMinor`, and CI reads the SDK from `global.json` (`setup-dotnet` with `global-json-file`). The test project targets `net10.0` like the API. Do not add a second SDK pin anywhere (a workflow `dotnet-version`, a test-only `global.json`), and do not switch `global.json` to the Microsoft.Testing.Platform runner (`"test": { "runner": ... }`) in one repo: the analyzers, the runner mode and the coverage collector are the same in every repo, or the scripts cannot check them.

## How the harness works

A typical test sends an HTTP request to the application hosted in process, through the real routes, middleware, claims transformer, handlers, AutoMapper profiles and a real PostgreSQL database, then asserts on the response and on what changed in the database. Only collaborators that leave the process are replaced.

**Three base classes, one per seam.** Each app has thin `DatabaseTestBase`, `ApiTestBase` and (optionally) `ServiceTestBase` in `<Tests>/Support/`, over the shared generic cores:

- `DatabaseTestBase` (over `DatabaseTestBase<TContext>`): `Db`, a context over a database no other test can see; `NewContext()`, another context over it for re-reading through a cold change tracker (the caller owns it); `ReadBack(db => ...)`, the same read in one expression, disposing the context; `Session`; `Mediator`, the substituted mediator a test's own contexts publish entity events to; `Ct`, the test's cancellation token; `Seed(...)`; `WaitUntil(condition, what)`; `Fixture`.
- `ApiTestBase` (over `ApiTestBase<TContext>`): `Root`, an actor holding every system permission seeded before each test; `RootClient`; `Actor()` to seed another actor; `Client(actor)`; `Client()` with no identity (a 401); `ReadAsync<T>` (with the app's `JsonSerializerOptions` where its `AddJsonOptions` adds converters), `AssertStatus`, `AssertProblem` (the `application/problem+json` shape, returning the `ProblemDetails`), `AssertJsonError` (the `application/json` body an MVC `JsonExceptionFilter` writes, alloy.api, cite.api, steamfitter.api; `AssertJsonError<TError>` for an app's own error type); `Factory`, the host, with its recorders.
- `ServiceTestBase` (optional, with `ApiTestHost`): a container built per principal, for services constructed with options a test chose. Only where the hosted application reads those options once for the run. No request, so no authentication handler and no claims transformer run: the principal comes from `ClaimsPrincipalBuilder` and stands for the transformer's output, while the authorization service and handlers stay real (CONVENTIONS.md section 1 says when that is allowed and what still needs an HTTP test).

**Fixtures.** `DatabaseFixture` is an xUnit v3 assembly fixture (`[assembly: AssemblyFixture(typeof(DatabaseFixture))]` in `AssemblyFixtures.cs`) over the shared `PostgresTestDatabase<TContext>`. It starts `postgres:16-alpine` on the first test that asks for a database, migrates a template database once with the app's real migrations, and gives each test its own database with `CREATE DATABASE ... TEMPLATE` (a file copy), dropped `WITH (FORCE)` afterwards. Tests that need no database run without Docker. The app factory is either run-wide (an assembly fixture, player.api's shape, the default) or per class (`IClassFixture`, blueprint.api's and vm.api's shape) when tests must assert on NSubstitute doubles registered in the host.

**Isolation.** The database is per test and the host is per run (or per class). Per-test databases rather than a rolled-back transaction, because `Crucible.Common.EntityEvents`' `EntityEventInterceptor` publishes on `TransactionCommitted` and discards on rollback, so transaction isolation would silently stop every entity event. Everything the application registers as a singleton is shared by the tests that use the host, and those tests run in parallel; that is the one place a test can interfere with another.

**What is real and what is not.** The factory boots the real `Startup` (through `Program`, see the pitfalls) with three replacements:

- **Token validation.** `TestAuthHandler` mints the identity a validated token would carry (`sub`, `name`, and the `scope` claims from `Authorization:AuthorizationScope`) from the `X-Test-User` and `X-Test-Name` headers. The app's real claims transformer then derives every permission claim from the database, so what an actor may do is decided by the rows `TestActor` seeded, never by claims the test wrote. What else a token carries is opt-in, for the code that reads it: `email` from `X-Test-Email`, a request's own scopes from `X-Test-Scope` (a machine-to-machine caller), `iss` from `TestAuthentication:Issuer`, and the user read from `Authorization: Bearer <user id>` with `TestAuthentication:UserFromBearer` (the `?bearer=` and `access_token` promotions SignalR connections use). It is registered under `TestAuthHandler.SchemeName`, or under the app's own scheme name where a hub or controller names it (`[Authorize(AuthenticationSchemes = "Bearer")]`, remove the app's `IConfigureOptions<AuthenticationOptions>` first, because `AddScheme` refuses a duplicate name: the Bearer recipe in `AppFactory.template.cs`, from alloy.api, blueprint.api and cite.api).
- **The context registration.** `TestDatabaseScope.ReplaceRegistration<TContext>` registers the context so that a request resolves the database of the test that sent it, by the `X-Test-Session` header. The request scope is the context's `ServiceProvider`, as in production, so entity events reach the real handlers.
- **The collaborators that leave the process**: hub contexts (`HubRecorder<THub>`; a per-class factory whose tests connect real SignalR clients keeps that hub's real `IHubContext`, vm.api's `ProgressHub`; a real connection goes over WebSockets through `Factory.Server.CreateWebSocketClient()`, because under long polling a hub invocation has no request carrying `X-Test-Session`, CONVENTIONS.md section 1), `IHttpClientFactory` (`StubHttpClientFactory` over `StubHttpMessageHandler`, with the base addresses of named clients production configures), hosted services (removed; each driven directly by its own test), and app-specific ones (player.api's `WebhookRecorder`; blueprint.api's and vm.api's sibling-API clients, substituted in a per-class factory). An app that delegates authorization to a sibling API substitutes that API's generated client and keeps its own service that interprets the answers (vm.api: `IPlayerApiClient`, not `IPlayerService`; CONVENTIONS.md section 1). The one in-process substitute allowed is a service that does nothing under the shipped configuration (blueprint.api's `IXApiService`), with the rule CONVENTIONS.md section 1 gives.

**The recorder rule.** Nothing registered in a run-wide host may be a substitute a test asserts on. It is one instance for the whole run, NSubstitute keeps its assertion state per thread, and `TestServer` serves requests on the pool the tests run on, so a pending `Received()` in one test can consume a call made for another. Those flakes arrive with load rather than with a change. A recorder keeps what it was given and a test reads it by naming the audience or url it expects (`Factory.Hub<ViewHub>().ToGroup(view.Id)`, a url of its own on `Factory.OutboundHttp`). Substitutes are fine where one test owns them: a test's own `Mediator`, an `ApiTestHost`, a `HubHarness`, a per-class factory. `check-repo.js` fails a run-wide factory that calls `Substitute.For`.

**Harness self-tests.** `DatabaseHarnessTests`, `HttpHarnessTests` and `TestActorTests` check what the rest of the suite assumes: two tests inserting the same key into a uniquely indexed column do not see each other (and a second insert of that key within one test is refused, which proves the index the probe relies on), explicit ids survive, saving publishes entity events, the real migration history and snake_case naming are in force, a request with no identity is a 401 and an actor with no permissions is refused, a request reaches its test's database, and each actor shape produces exactly the claims it promises. When the harness breaks, these fail instead of a hundred unrelated tests. `verify.sh` requires all three to exist and pass.

## Defect documents

A defect a test finds is characterized by an ordinary passing test of the current behaviour, and described in `/mnt/data/crucible/agent-docs/api-test-bugs/<app>.md` (for example `player.api.md`), outside every repo. The test carries at most a one-line `/// <summary>` stating the current behaviour neutrally. The document's format is in [../testing/README.md](../testing/README.md), "Defect documents"; this stack's rules are CONVENTIONS.md section 3. Two scripted checks, both run by `verify.sh`, hold the line on defect text in code: `check-repo.js tests` fails defect phrases in test comments, wrapped across lines or not, and `check-repo.js defects` fails a test the document names that carries more than the one-line summary. That each entry's test exists, by file and name, and the document's counts and shape, are NOTE lines; `../testing/fix-docs.js` fixes most of them.

## Known pitfalls

- **`diagnosticMessages` hangs the run.** Setting it in `xunit.runner.json` produces the provider banner but the run then hangs after the last test and never reports completion (SDK 10.0.103, VSTest 18.0.1, `xunit.v3` 3.2.2). Pass `-- xUnit.DiagnosticMessages=true` on the command line instead, as CI and `verify.sh` do. The shared `xunit.runner.json` holds the schema only, and `sync.sh` keeps it that way.
- **The banner is the proof of the provider.** The VSTest bridge discards the test host's stdout, so `PostgresTestDatabase` writes its banner (`[<Tests assembly>] database provider: PostgreSQL ...`) as a console line and as an xUnit diagnostic message, and CI greps the latter. It prints once, when the first test asks for a database.
- **cobertura counts every class twice.** coverlet's cobertura output emits each class element twice; merge hits per file and line before summing, or read `lines-covered` and `lines-valid` on the root element, which are already merged. Adding class elements up doubles every count and keeps the ratio, which is what makes the mistake easy to miss.
- **`uuid-ossp` needs a superuser.** The migrations emit `CREATE EXTENSION "uuid-ossp"`. The official image's `postgres` user is a superuser; never configure the container with a restricted role.
- **Template clones fail while the template has a connection.** Npgsql returns disposed connections to its pool, so `PostgresTestDatabase` clears the template's pool after migrating. Nothing may connect to the template again; a host that needs a database of its own gets a clone.
- **NuGet audit warnings stay warnings.** `TreatWarningsAsErrors` would turn the NuGet audit (NU1901-NU1904, mostly AutoMapper 13 and MediatR 12, pinned for licensing, and transitive packages), NU1510 and TinCan's NU1701 into build failures nobody can fix from a project file. The shared `Directory.Build.props` lists them in `WarningsNotAsErrors`; `verify.sh` allows only those codes.
- **`HostFactoryResolver` falls back to `Program.Main`.** Every Crucible API's `Program` has `CreateWebHostBuilder(args)` returning an `IHostBuilder`, which matches neither convention `HostFactoryResolver` looks for (`CreateHostBuilder`, `BuildWebHost`, top-level minimal hosting). `WebApplicationFactory` then runs `Program.Main` on a background thread and intercepts the host it builds, and `Main` runs to completion, `InitializeDatabase()` included. Either the app has a production switch that skips it (player.api's `open-api-only`, passed with `UseSetting` because host settings reach `Main` as `--key=value`), or the host gets a throwaway database cloned from the template (`AppFactory.template.cs` step 1B: alloy.api, caster.api, cite.api, gallery.api, steamfitter.api; and both per-class factories). Never point the host at the template.
- **`InitializeDatabase` resolves the context outside a request, and publishes entity events.** It opens a scope of its own while the host starts, so the one-argument `TestDatabaseScope.ReplaceRegistration` (which routes by the request's `X-Test-Session` header) throws there. Step 1B uses the two-argument form: until the host has started, a resolution outside a request gets the host's own database, built over that session's own services rather than the resolving scope; after that it throws again, so a stray resolution still fails loudly. The services matter because the seed's saves publish entity events: built over the host's scope they reach the real handlers and the hub recorders (blueprint.api's seed broadcasts landed in its `MselUnit` tests' recordings and made them flaky); built over the session's services they go to its substituted mediator, which nothing reads.
- **`WebApplicationFactory.StartServer` takes no lock.** Two tests asking for their first client at once each build a host, each running `Program.Main`; with step 1B the second `InitializeDatabase` then runs after the startup window has closed, and throws (steamfitter.api; caster.api saw it under coverage). Every way into the host (`CreateClient` in either overload, `CreateDefaultClient`, `Services`, `Server`) goes through `StartServer` to `CreateHost`, so the run-wide template overrides `CreateHost` to build one host under a lock and hand it to every caller. A lock around `CreateClient()` alone (one repo's first version) is bypassed by `Factory.Services`, `Factory.Server` and `CreateClient(options)`. A per-class factory needs no lock: one class's tests run one after another.
- **The claims cache is keyed on user id.** A run-wide host would let one test's permissions answer another test's request; `TestConfiguration` turns `ClaimsTransformation:EnableCaching` off. A test whose subject is the cache drives it directly.
- **`ProblemDetails` shape depends on the environment.** The run-wide template hosts with `UseEnvironment("Production")` so the exception middleware answers as deployed. MVC apps whose `JsonExceptionFilter` puts the message in the body only in Development (blueprint.api) host in Development and say so in their factory.
- **Minimal-API apps bind at registration.** In player.api (minimal-API `IEndpoint` slices) anything a handler parameter cannot resolve as a service is inferred as a body and rejected on a GET; harnesses that map endpoints without the host register the services the delegates inject.
- **`dotnet test` needs Docker.** Only for tests that take a database; the container starts lazily, so a machine without Docker still runs the pure unit tests and every database test fails at once with one message naming the missing daemon.
