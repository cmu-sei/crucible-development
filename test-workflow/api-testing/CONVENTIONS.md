# Conventions for Crucible API tests

How tests are written in every Crucible API. `dotnet-test-writer` follows this file and `api-test-reviewer` reviews against it, so a rule that is not here, in [../orchestration/RULES.md](../orchestration/RULES.md) or in the formats of [../testing/README.md](../testing/README.md), is not a review criterion. Only `test-standard-maintainer` edits it, at a standard version; changes are listed in [CHANGELOG.md](CHANGELOG.md). The harness itself (fixtures, factories, shared files, pitfalls) is in [README.md](README.md). Rules marked **house style** were established by player.api's suite (the reference) rather than by Microsoft's guidance; they stay, so every repo reads the same.

## 1. Conventions every test follows

- **License header** on every new file:

  ```csharp
  // Copyright <current year> Carnegie Mellon University. All Rights Reserved.
  // Released under a MIT (SEI)-style license. See LICENSE.md in the project root for license information.
  ```

- **xUnit v3 only.** `[Fact]` and `[Theory]` from `xunit.v3`, assertions from `Xunit.Assert`, doubles from NSubstitute. No xUnit 2, no FluentAssertions, no Moq.
- **Names are sentences** (house style). `Create_persists_the_view_and_returns_it`, `Edit_is_forbidden_without_ManageViews`, not `TestCreate2` or `Create_Valid_ReturnsCreated`. The failure summary is all a reader of CI output gets, so it reads as a statement about the application. The leading word is the operation under test where there is one, which keeps Microsoft's method / scenario / expected-behaviour parts, written as prose.
- **No Arrange, Act and Assert comments** (house style). A blank line between the three parts shows the shape; comments explain what a test characterizes and why it matters, not what the next line does. No commit hashes, issue numbers or dates in test comments either: the history is git's, and a hash in an uncommitted worktree names nothing.
- **One Act per test** (Microsoft's "avoid multiple acts"): a second request whose result is asserted is a second test. Two things are not a second Act:
  - **Reading the effect.** A write's effect read back through `NewContext()`/`ReadBack`, a recorder, or a run-wide singleton read from `Factory.Services` and keyed to the test's own ids. Where the only place an effect shows is another endpoint, a side-effect-free GET after the Act is an assertion read; prefer the database where it shows there too.
  - **One control request in a denial test.** A denied test may assert, after the denial, one control request that succeeds and differs from the denied one in exactly one thing (the resource, or the caller's one permission), when the control is what proves the near miss is a working grant rather than an actor the transformer gave nothing. The name says both halves (`Get_is_forbidden_on_another_view_but_allowed_on_its_own`). More than one control, or a control that writes, is a second test.
  - **A read-only precondition.** An assertion on the arranged state before the Act, read through the database (`ReadBack`, `NewContext()`) or a recorder, is an arrange check and may stay. A precondition read through a request is a second request whose result is asserted: its own test.
  - **A comparison.** Two side-effect-free requests whose agreement is the subject (a list against the get of one of its rows) are one Act. When either writes (a preview, then the import it predicts), they are two tests. Two callers sending the same request, one answered 500 and one 200, are two Acts too: two tests.
- **`Ct` everywhere** (house style, enforced by xUnit1051 under `TreatWarningsAsErrors`). Pass `Ct` (`TestContext.Current.CancellationToken`) to every awaited call that takes a token, so the runner can cancel a test blocked on a PostgreSQL lock. Where a call must use a token-less overload, name it in a private helper, which says "deliberately" once.
- **Real assertions over call counts.** Whether something was saved is answered by reading it back, not by verifying that `SaveChangesAsync` was called. `Received()` is for collaborators that leave the process and have no state to read (a test's own `Mediator`, an `ApiTestHost` substitute, a `HubHarness` proxy).
- **Re-read through a cold context** (house style). Assert on the database through `NewContext()` or `ReadBack(db => ...)`, never on the seeded objects still held or on `Db` after a request: each request runs in its own scope with its own context, so `Db`'s change tracker never saw the write. Scope the context with `await using`, or read in one expression with `ReadBack`, which disposes it. Where a file re-reads the same table in several tests, a private `Stored()` helper over `ReadBack` is fine.
- **Seed with object mothers and actors.** Entities come from `TestData` mothers (add one when a second test needs the entity; no entity built inline twice). Callers come from `Actor()`, which seeds the rows the real claims transformer reads, including group memberships and the join rows a gate reads (`InGroup`, blueprint.api's `InUnit`), never a membership row a test seeds by hand. A connected set of rows that many tests need (an evaluation with its teams, moves and scoring model) may be a **seed-graph helper**, an allowed extra in `Support/` named for the graph it builds (cite.api's `TestScenario`, blueprint.api's `MselGraph`), built from `TestData` mothers and returning the entities it saved; it seeds no actors.
- **Never fake authorization.** An HTTP test's caller is `Root`, an `Actor()`, or `Client()` with no identity. Its permissions come from seeded rows through the app's real claims transformer and real handlers, never from claims the test wrote, a substituted `IAuthorizationService`, or a policy override. `ClaimsPrincipalBuilder` has two uses:
  - **Tests of the authorization stack itself** (requirement handlers, the authorization service, the claims service). There it builds shapes the transformer cannot produce (`WithRaw*`, a permission claim written with `WithClaim`, an unparseable value).
  - **Service tests on `ServiceTestBase`.** They construct a service in an `ApiTestHost`, with options the test chose and no request at all. That container has no authentication handler and no claims transformer, by design, so the principal the service reads stands for the transformer's output, and the builder is how a test writes it. The authorization service and the handlers in the host stay real and read that principal as in production.

  - **Hub tests on `HubHarness`.** A hub method invoked directly has no request either, so the caller is a `ClaimsPrincipalBuilder` principal handed to `HubHarness`, and the app's real authorization service and handlers decide on it, as in a service test (never a substituted authorization service in a hub test). Per-method gates inside the hub are tested this way; the hub's own `[Authorize]` (its scheme and policy) gets at least one test over a real SignalR connection to the in-process `TestServer` per hub: an `Actor()` connects, `Client()` with no identity is refused. Connect over WebSockets (`HttpTransportType.WebSockets`, `SkipNegotiation`, and a `WebSocketFactory` that opens `Factory.Server.CreateWebSocketClient()` with the actor's `X-Test-User`, `X-Test-Name` and `X-Test-Session` headers: cite.api's `MainHubConnectionTests`). Under long polling a hub invocation runs outside any request, so `TestDatabaseScope` finds no `X-Test-Session` header and cannot pick the test's database; blueprint.api's factory falls back to the host's database for it, which works only while the method reads nothing the test seeded. Where the hub class names its scheme (`[Authorize(AuthenticationSchemes = "Bearer")]`, every Crucible hub class but caster.api's, whose `[Authorize]` is plain, and vm.api's), the factory registers the test handler under that name too (`AppFactory.template.cs`, the Bearer recipe). vm.api's mapped hubs (`Features/Vms/Hubs/VmHub`, `ProgressHub`) carry no attribute: `MapHub<T>(...).RequireAuthorization()` in `Startup` gates them with the default policy under the default scheme (Bearer in production, the test scheme in the factory), and that mapping is the hub's connection gate; the only Bearer attribute there is on the unmapped duplicate `Hubs/VmHub.cs`, which nothing reaches. The allowed connection is an `Actor()`, never `Root`. The test needs `Microsoft.AspNetCore.SignalR.Client` at the version `test-packages.props` pins; in a repo with central package management that is a `PackageVersion` line in the repo-root `Directory.Packages.props` (player.api, blueprint.api, vm.api). A real-connection test does not exercise the `?bearer=` / `access_token` query-string promotion: that is token validation, which `TestAuthHandler` replaces by design (`TestAuthentication:UserFromBearer` is the opt-in for code that reads the bearer value).

  A hub method test on `HubHarness` ends with `harness.AssertAddressedOnly(nameof(IHubCallerClients.OthersInGroup), ...)`, naming every audience the method may address, or `harness.NothingAddressed()`: the harness's proxies are substitutes, so a hub that also sends to `All` or `Others`, or reads `Context.Features` or aborts the connection, passes a test that only reads the group it expects. `harness.Addressed` lists the audiences in order.

  The price of the second and third uses is that a service or hub test cannot catch a transformer that derives the wrong claims from rows. So: where a route reaches the service, its gate is still tested over HTTP with `Actor()` (section 4); `TestActorTests` and the claims service's own tests pin the claim shapes the builder mirrors; and in a service test, permission claims come only from the builder's typed steps (`WithSystemPermissions`, `With<Resource>`). `WithClaim` is fine there for a claim the identity provider issues and the transformer passes through (`iss`, a client claim), never for a permission. A service test's denied cases are near misses like any other, and an `ApiTestHost` never substitutes the authorization service.
- **Recorders, not run-wide substitutes** (house style; README, "The recorder rule"). In a run-wide host, assert on a key no other test uses: the group a seeded id produces on `Factory.Hub<THub>()`, a url of your own on `Factory.OutboundHttp`, a payload containing a name unique to the test. Asking whether a hub broadcast *anything* asks about the whole run. Route rules, `RefusesUnmatched()` and `FailsFor(...)` belong on a recorder or handler one test owns, never on the run-wide one.
- **Substitutes in a per-class factory** are for what leaves the process (a sibling API's client, a hypervisor). The one in-process exception is a service whose real implementation does nothing under the shipped configuration (blueprint.api's `IXApiService` with `XApiOptions:Enabled` false): substituting it turns a no-op into an observation point. A test that asserts on such a substitute shows only that the call was made; what the service does with it is asserted through a factory that restores the real service with the configuration that enables it (blueprint.api's `XApiEnabledFactory`), at least once per call the substitute stands for.
- **An app that delegates authorization to a sibling API substitutes that API's client, not its own service.** vm.api asks player.api whether a caller may act; the seam is the generated `IPlayerApiClient`, with per-caller answers, and vm.api's own `PlayerService` (which turns those answers into decisions, `PlayerService.Can`) stays real. A substituted `IPlayerService` would be a substituted authorization service. Mind what the real service caches: `PlayerService` keeps a caller's system permissions for a minute in the host's `IMemoryCache`, keyed on the user id (`PlayerService.cs:515-521`), so each test uses actors of its own and never changes one actor's answers mid-test. The double that answers for the sibling (vm.api's `PlayerDirectory`) mirrors that API's own visibility and authorization on every route it answers, and has self-tests pinned against the sibling's source (each one names the sibling's `file:line` it mirrors in its summary): who sees which teams, which listings take a privileged caller, what a scoped claim without permissions grants. A double more permissive than the sibling makes every denial test above it pass for the wrong reason; vm.api's first version answered the roster without the primary-visibility filter and privileged listings for any caller, and no test noticed. The double answers every route production calls on the sibling; a test does not stub a sibling route ad hoc on the client (vm.api's `GetUserAsync` and `GetTeamUsersAsync` in `VmHubGroupTests`) unless the double has that route under the same self-tests.
- **`[Theory]` only for data-only variation** (house style). A theory is for cases that differ only in data (a route table, a list of status codes). `_is_forbidden_` and `_not_found` tests stay `[Fact]`s, however alike they look, when what distinguishes them is the permission the caller holds or the entity the id does not resolve to: rolling those up moves the distinguishing part into a lambda in `TheoryData`, which xUnit cannot serialize, so a failure reports a case index where a sentence belongs. The one denial theory allowed is a **route table**: one actor and one permission held, rows that are strings only (method and route, `[InlineData("DELETE", "api/views/{0}")]`), so each failure names its route (`Every_write_route_is_forbidden_for_a_caller_holding_only_ViewViews`).
- **No logic in tests, no magic strings.** No `if`, loops or string building around assertions (Microsoft's "avoid logic in tests"); a value whose meaning is not obvious is a named constant (`private const string SharedName = "Isolation Probe";`) with a doc comment saying why that value.
- **Helpers over setup.** Shared arrange code is a private helper the test calls (`Service()`, `Stored()`, `SeedViewWithTeam()`), not state built in the constructor for every test (Microsoft's "helper methods instead of setup and teardown"). The base classes' `InitializeAsync` (a database, `Root`) is the exception the harness owns.
- **Doc comments** say what a test characterizes and why it matters, in a `/// <summary>` (and `/// <remarks>` for the reasoning) over the test or the class. Not required on every test; required where the reason is not in the name.
- **No skipped tests.** `[Fact(Skip = ...)]` fails the build (xUnit1004 raised in `.editorconfig`). A test that has nothing to assert under some condition uses `Assert.SkipWhen` / `Assert.SkipUnless` and says why in the message. `check-repo.js tests` prints a NOTE line for every dynamic skip; the reviewer accepts one only where its condition turns false without editing the test (player.api's `Every_source_validated_map_consumes_every_source_member` runs as soon as the first `MemberList.Source` map exists). A skip that holds in every run of every configuration is dead code: delete the test (with its accounting line, section 2) or make it assert.
- **`WaitUntil` is a last resort**, for background services whose work starts in their constructor and completes nowhere a test can await. Prefer a signal to await, or an effect that queues behind a later, observable one (player.api's `BackgroundWebhookServiceTests` sends a second, subscribed event as a barrier).
- **Dispose what you create.** A `NewContext()` (`await using`, or `ReadBack(db => ...)`, which disposes it; `check-repo.js tests` fails an inline `NewContext().X`), a `StubHttpMessageHandler` of your own, an `ApiTestHost`. An undisposed context keeps its pooled connection checked out for the rest of the run, and one PostgreSQL server serves the whole suite.
- **A hosted service a test starts, the test stops**: `StartAsync`, act, `StopAsync` in a `finally`, so no loop outlives its test. Where `StopAsync` does not stop the loop (the loop ignores its stopping token, or runs on a `Task.Run` it never awaits), that is a defect entry, and the tests drive the loop's unit of work (the method one iteration calls) rather than the loop, so the suite does not leak one loop per test.

## 2. Adding a test

1. Put the file where the code under test lives, mirroring the API project: a request in `Features/<Area>/`, a controller in `Controllers/`, a service in `Services/`, a hub in `Hubs/`, an event handler in `Events/`, infrastructure in `Infrastructure/<Area>/`. Read the `namespace` line of the production file rather than inferring it from the path; they do not always match.
2. Derive from `ApiTestBase` if the test sends a request, `ServiceTestBase` if it constructs a service with options of its own (only in repos that adopted it), `DatabaseTestBase` if it only needs a database, or nothing at all (a converter, a requirement handler with `AuthorizationHarness`, a hub with `HubHarness`).
3. Forward the fixtures: `public class XTests(DatabaseFixture fixture, AppAppFactory factory) : ApiTestBase(fixture, factory)`; in a repo with the per-class factory add `, IClassFixture<AppAppFactory>`.
4. Seed with `TestData` mothers and `Actor()`. Name the method as a sentence. Pass `Ct`.
5. Assert on the response (`ReadAsync`, `AssertStatus`, `AssertProblem` for `application/problem+json`, `AssertJsonError` for an MVC `JsonExceptionFilter`'s `application/json` body) and on the database through `NewContext()` or `ReadBack`.

**Layout.** The test project mirrors the API project; `Support/` holds the harness: `Support/Shared/` the shared files (never edited in a repo), `Support/` the template-derived files and allowed extras. The harness self-tests (`DatabaseHarnessTests`, `HttpHarnessTests`, `TestActorTests`, and `ApiTestHostTests` where `ApiTestHost` exists) live in `Support/` too.

**Removing or replacing a test.** No behaviour a test asserts is lost when a test is renamed, rewritten, merged, split or deleted (a `[Fact]`, a `[Theory]` row, a whole file).

- **The narrowing rule.** A replacement asserts at least every observable the removed test asserted: every status, every member of a body, every stored row, both sides of a navigation, call ordering, cancellation-token forwarding, every row of a theory (a theory split into facts keeps every row). What the old test asserted inside its fake handler or stub counts the same (the request method, the path, that every request matched a pattern, the order of calls): the successor asserts it on the recorder or the handler it owns. "Asserts the real behaviour instead of a substitute" never licenses asserting less. A construction-only test (`Assert.NotNull(service)`) is replaced by a behaviour test of the same class at the same path, not deleted.
- **The accounting.** Every removed method, and every removed row of a theory that stays, is matched by `check-repo.js removed` (moved, renamed with an identical body, rows merged) or has a line in `/mnt/data/crucible/agent-docs/api-test-bugs/<app>.removed-tests-<date>.md`, in the notation of [../testing/README.md](../testing/README.md), "Removed-test accounting" (`Class.Name` and a folder prefix are fine for the old test). A test whose path another test covers is merged (B) into it; that is no licence to collapse cases (RULES, Test quality: suites keep their size). `verify.sh` fails an unaccounted removal.
- **Ratchets.** Thresholds and counts only go up: never set a coverage threshold below the value on `main`, and a test count falls only by accounted removals.

**Common mistakes** (each one cost a flake or a false green in the reference suite):

- Reading `Db` after a request. The request had its own context; re-read through `NewContext()`.
- Asserting on the shared surface of a run-wide host ("the hub broadcast something", "two webhooks were queued") instead of a key the test owns. Passes or fails depending on what else ran; reproduces only under load, which is why the reviewer's check is a repeated run under coverage collection rather than one plain run.
- Reaching for a substitute to answer that question instead. See the recorder rule.
- `ServiceTestBase.HostFor(user, configure)` honours `configure` only on the call that builds the host; a later call for the same principal throws. Build a principal per configuration.
- Denied cases with an empty grant (section 4).
- A near-miss actor on a team (or other resource) from a `TestData` mother whose default role grants, so it holds more than the test names (section 4; use `OnNew<Resource>`).
- A request left running when the test returns. `TestDatabaseScope` releases the session first, so the stray request fails naming the header; await everything.
- A route rule (`Answers("GET api/views/*", ...)`) or `RefusesUnmatched()` on the run-wide `Factory.OutboundHttp`. It answers, or refuses, every test's matching request; arrange an absolute url of your own there, and rules on a handler the test owns.
- An allowed case run as `Root`. `Root` holds everything, so the test does not show which permission the gate requires; the allowed case holds exactly the required permission (section 4).

## 3. Defects: a test in the code, the description in the document

- **Characterize, don't fix.** If the code under test has a defect, the test asserts the *current* behaviour with an ordinary passing test, and the defect is described in the app's defect document, `/mnt/data/crucible/agent-docs/api-test-bugs/<app>.md` (for example `player.api.md`), outside every repo. Don't change production code unless the task says to. The test passes today and fails once the defect is fixed; the entry tells the fixer which test that is. Never park a defect with `Skip`.
- **No defect notes in code.** A test file carries no defect description, no expected behaviour, no fix, and none of the capitalized defect tag, `FIXME`, "turns red", "goes red", "flip to", "characterizes current behaviour", "ever fixed", or "once / when / if / until this (it, that) is fixed" in any comment. `check-repo.js tests`, run by `verify.sh`, fails them as `PIN`: it reads each run of consecutive `//` or `///` lines, and each `/* ... */` block, as one text, so a phrase wrapped across two lines is found, and it names the run's first line and the lines the phrase is on. The script catches the phrases; the reviewer catches the prose (a `<remarks>` block that explains a defect without using any of them). A test that characterizes a defect may carry a one-line `/// <summary>` (one `///` line holding the whole `<summary>...</summary>`; `check-repo.js defects` fails two) stating the current behaviour neutrally (`/// <summary>A duplicate name on edit is answered with a 500.</summary>`) and nothing more: no "wrong", "should", "ought", "until", issue number or remarks block. The test name states the current behaviour too (`Edit_answers_a_name_that_is_already_taken_with_a_server_error`). Everything else goes in the entry.
- **The entry.** The format of an entry and of the document is in [../testing/README.md](../testing/README.md), "Defect documents": `### <test name>` under `## <test file path>`, the heading the exact method name, and ``Test: `<test file path>` `<method name>` ``. Paths are from the repo root, or from the API project where that is unambiguous. What this stack adds:

  **A characterized 500 asserts its `Detail`** (`AssertProblem(...)` or `AssertJsonError(...)` returns it): the exception message is what proves which throw the entry's `file:line` names. cite.api's unknown-submission entry cited `SubmissionService.cs:715` and a Fix to match, while the message showed the throw was `AuthorizationService.cs:291`. Hosted as in production (the run-wide template's `UseEnvironment("Production")`), the exception middleware and `JsonExceptionFilter` put only the message in `Detail`, never a stack frame. Where the message is generic (`NullReferenceException`, `DbUpdateException`), assert it all the same, and add an assertion on the state the throw left (the stored row, a recorder) where that tells the throws apart; the entry's `file:line` carries the rest. A service-level defect test, with no response, asserts the exception's type and, where either identifies the throw, its message or `ParamName`.

- **Cross-repo consumers.** The consumers a `Cross-repo;` entry names are the UIs' generated clients (blueprint.ui's `src/app/generated/`), the other APIs' NuGet clients (`Blueprint.Api.Client`), the Terraform provider and the Moodle plugins; a library such as `Crucible.Common.EntityEvents` is a repo too. A fix that changes nothing a consumer can see is not cross-repo, whichever files it touches.
- **The same defect in another test.** Another test that touches a defect with an entry gets no entry of its own; at most the comment `// Same case as <Test>.` (a test in the same file) or `// Same case as <Class>.<Test>.` (another file), on its own line above the attributes, naming an entry or a "Needs a decision" item. `check-repo.js defects` notes any other form and any name it cannot resolve.
- **A shape test needs a vehicle.** A test of the exception middleware's or filter's answer to an unhandled exception (section 4, item 4) needs some defect to produce the 500. It carries `// Same case as <the entry's test>.`, and that entry's `**Test to flip:**` names the shape test too, which then needs another vehicle (or, with none left, is deleted), so fixing the defect does not leave a red shape test nobody expected.
- **Recurring patterns.** Characterize every instance. Where one pattern repeats across handlers (a unique index surfacing as a 500 because the handler saves without checking, a missing body answered with a 500), either one `[Theory]` over a route table with one entry that lists each affected production `file:line`, or one test per handler with a shared recipe; the document's recipe gives the fix once and each entry's `**Fix:**` names it. A latent instance (a method no route reaches, or an input no caller can produce) carries the latent marker of the shared format, naming the callers and what stops them.
- **Canonical form** (illustrative names and line numbers), the test:

  ```csharp
  /// <summary>A name another role holds is answered with a 500 on edit.</summary>
  [Fact]
  public async Task Edit_answers_a_name_that_is_already_taken_with_a_server_error()
  {
      var taken = TestData.Role("Taken");
      var role = TestData.Role("Mine");
      await Seed(taken, role);

      var response = await RootClient.PutAsJsonAsync($"api/roles/{role.Id}", new { name = "Taken" }, Ct);

      await AssertProblem(HttpStatusCode.InternalServerError, response);
  }
  ```

  and its entry:

  ```markdown
  ## Player.Api.Tests/Features/Roles/RoleRequestTests.cs

  ### Edit_answers_a_name_that_is_already_taken_with_a_server_error

  Test: `Player.Api.Tests/Features/Roles/RoleRequestTests.cs` `Edit_answers_a_name_that_is_already_taken_with_a_server_error`

  Roles/Requests/Edit.cs:48 saves the new name without the duplicate check Create.cs:41 makes, so the
  unique index on `roles.name` refuses the save and ExceptionMiddleware answers 500 with the database
  message. Expected: 409 Conflict, as Create answers.

  **Fix:** Recipe A. In `Player.Api/Features/Roles/Requests/Edit.cs:48`, check the name as `Create` does before saving.

  **Test to flip:** `Edit_answers_a_name_that_is_already_taken_with_a_server_error` (expect `AssertProblem(HttpStatusCode.Conflict, ...)`; the stored name stays "Mine").
  ```

- **What the script checks.** `check-repo.js defects <repo> <app>`, run by `verify.sh`, fails a test an entry or a "Needs a decision" item names that carries more than a one-line `/// <summary>` or a `<remarks>` block: defect text in code. Everything else it reports is a NOTE: a named test it cannot find in the named file, the document's sections and their order, the `**Fix:**` and `**Test to flip:**` lines, a description that starts lowercase, the intro and summary counts, the recipes, "Found without a test" items without a `Reason:` or that are tests of the repo, and `// Same case as` comments. `../testing/fix-docs.js` rewrites line pointers, follows renames and recounts.
- **Recurring defects to look for.** The reference suite found most of these:
  - A uniquely indexed column saved without a check, so a client's duplicate is a 500 rather than a 409 (create and edit and add-to-role alike).
  - A missing or `null` request body dereferenced in the endpoint or passed to MediatR, answered with a 500 rather than a 400.
  - An out-of-range enum value accepted and stored.
  - A cancellation token accepted by the endpoint and not passed on, so a cancelled request keeps writing.
  - Files written before the row that owns them is saved, so a rejected request leaves orphans on disk.
  - A clone or import that copies some child collections and not others.
  - An authorization check on the parent resource only, so a child of another resource is reachable by id.
  - An update that authorizes the stored parent, then maps the body's parent id onto the row, so a caller allowed on one parent moves the row under another parent it may not touch. Look for it on every update whose body carries a parent id.
  - A collection gate that authorizes one arbitrary member and returns all of them (the first member's permission answers for every member of the collection).
  - A membership or role update that lets a caller grant itself, or anyone, a role above its own. It is an entry, not a "Needs a decision" item: a caller holding only a user-management permission that makes itself Administrator is entered the same way in every app where it is found. The resource-membership form (a caller holding a resource's Manage permission makes itself, or anyone, that resource's Owner or Manager) is the same entry shape and gets one shared recipe per app. Before writing what "the caller sees", judge whether production can produce the caller: a permission set a documented endpoint can create is reachable (a custom role created through the app's roles endpoint); one that only seed data or a hand-edited database can create (a seed-only role) makes the entry `(latent: unreachable input)`, naming what stops it. A test seeding a role with explicit permissions (`On<Resource>(..., permissions: [...])`) mints such a role; check the shipped roles before calling the entry live.
  - A webhook or background sender that drops an event on a status it does not expect.

## 4. What to test, in priority order

1. **Endpoint authorization, allowed and denied per permission.** For every endpoint (minimal-API `IEndpoint` or MVC controller action), one test that a caller holding exactly the required permission succeeds, and one denied test per way of falling short. **Denied cases are near misses:** the denied actor holds a permission close to the required one (another permission on the same resource, the same permission on another resource or team, view where edit is required, a membership on a sibling team), never nothing at all. An actor with no rows cannot tell a broken claim filter from a working one. Where system, resource and membership permissions combine, cover each path that grants, a group membership included.

   **The allowed case holds exactly the required permission, and is never `Root`.** `Root` holds everything, so a test that succeeds as `Root` does not show which permission the gate requires, and a gate that asks for the wrong one passes it. `Root` is for tests about what an endpoint does, not who may call it.

   **The near miss asserts the gate's own refusal** wherever another step on the path answers the same status (a refusal of its own earlier on the path, as in player.api's `FileService` upload and update; a sibling double that refuses): it asserts the message (`AssertProblem` and `AssertJsonError` return the `Detail`), so the denied test fails when this gate is broken rather than passing behind the other refusal.

   **Two-tier gates whose second tier covers only some resources** (blueprint.api: a template MSEL's `CreateMsels` tier) need a near miss on that subset (a caller lacking `CreateMsels` on a template), or breaking that tier leaves every denied test passing. **A bypass gate**, a permission that skips a limit and refuses nobody (alloy.api's `EventService.ResourcesAreAvailableAsync`), has as its near miss a caller without the permission who hits the limit; where the limit answers 500, the gate is allow-listed with a `Defect:` reason naming that entry.

   **Each gate family needs a near miss on another resource.** A near miss that holds everything except the one permission asked (vm.api's `PlayerPermissions` "allow everything but `ManageViewMaps`") catches a gate that asks the wrong question, but not one that asks about the wrong resource: it holds the asked permission nowhere, so a gate checking the route's view and one checking some other view both refuse it. So for every gate family (the endpoints that check one permission on one kind of resource) at least one denied test holds the very permission the gate asks for, on another resource of that kind (`..._is_forbidden_for_a_caller_holding_ManageViewMaps_only_in_another_view`).

   **A resource mother's default role grants too.** Where a membership's permissions add to what the resource itself grants its members (player.api: a team's own role, unioned with the membership role), a `TestData` mother that defaults that role to a seeded one silently adds its permissions to every member. player.api's `TestData.Team(viewId)` defaults to the seeded `View Member` team role, which grants `ViewTeam` and four VM and map permissions. So `Actor().OnTeam(team, viewPermissions: [ViewView])` on such a team also holds `ViewTeam`. As the near miss of a `ViewTeam` gate it holds the very permission it is meant to lack. As the allowed case of a gate it may succeed through a permission the test never named, so the test does not show which permission the gate requires. Neither problem is visible in the test's text. Seed every near-miss actor with the builder's `OnNew<Resource>(...)` step (player.api: `Actor().OnNewTeam(view.Id, viewPermissions: [ViewPermission.ViewView])`), which mints a resource whose own role grants nothing, so the actor holds exactly what the call names. Pass an existing resource to `On<Resource>` only when the test is about what that resource grants. Do not hand-roll the step as a private helper in each test file; add it to `TestActor` once.

   `check-repo.js tests`, run by `verify.sh`, prints a NOTE line (never a failure) for a test that asserts `HttpStatusCode.Forbidden` or `ForbiddenException` and whose client is an actor seeded as `Actor().SeedAsync()` with no step between other than `WithId` or `WithName`, which grant nothing. Files under `Support/` are exempt, because `HttpHarnessTests` refuses an empty actor on purpose. The check reads text, so it warns rather than fails.

   **The scope requirement** (every Crucible API requires the configured scopes of every token, in its default policy and, in the MVC apps, a global `AuthorizeFilter` too) gets one denied case per configured scope and mapping family (controllers, hubs, the metrics endpoint): `TestAuthHandler.ScopeHeader` carrying every configured scope but one, refused, and one with all of them, allowed. Beside the route table, a **scope table** theory is allowed: one actor, rows that are strings only (`[InlineData("player")]`), so each failure names its scope.

   **A data-row gate.** Some gates read a row that is not a role or a membership the builder seeds: an invitation matched on the caller's email domain, a `CreatedBy`, the very membership row the endpoint is about (blueprint.api). The check stays quiet when the actor's id goes into a seeded row in the same method (`CreatedBy = actor.Id`, `createdBy: actor.Id`, `TestData.UnitUser(actor.Id, ...)`, `SeedCatalog(..., actor.Id)`). Where the row does not carry the actor's id, the test says so on a line of its own inside the method, naming the row: `// Data-row gate: the invitation seeded above, restricted to example.test, is the only grant.` The check stays quiet for it too, and the reviewer confirms the row is what the gate reads and that the denial is about it. Any other such NOTE is a should-fix, and the gates check never credits that denial as a near miss. The check cannot see a near miss that holds too much (the default-role pitfall above), so the reviewer still reads every denied test's actor.
   **The gates check: an untested gate is a blocker.** `check-repo.js gates`, run by `verify.sh` as a failure, inventories every authorization call site in the application and fails each one the tests do not cover with both an allowed case that is not `Root` and a near-miss denied case. A gate it reports is never a follow-up: the writer is done when the check reports none missing and none provisional, or every one left has an allow-list reason, and [ready](../GLOSSARY.md) needs the same. It reads text, so it states exactly what it recognizes, below; a test it cannot link is linked by hand, never left out.

   - **What it inventories.** A call on a service field (`_authorizationService`, `AuthorizationService`, `_playerService`, any receiver ending in `Service`) of `Authorize`, `Authorize<T>`, `AuthorizeAsync`, `AuthorizeAsync<T>`, `HasSpecificPermission`, `Can` or `Can<Something>` (vm.api's `CanViewVms`); a requirement's `IsMet` (blueprint.api's `MselOwnerRequirement.IsMet`); and a call to an app helper that takes permission arrays (vm.api's `BaseHandler.GetVm(id, AppSystemPermission[] ...)`) on its own type or on a service field named for it. A call counts wherever it is: a controller action, a MediatR handler's `Authorize` override (player.api's and caster.api's `BaseHandler`) or `Handle`, a service method (cite.api's `var hasPermission = ...`), a hub method, a private helper (credited to whoever calls it). The machinery is not a gate: anything under an `Authorization/` folder, in a type named `*AuthorizationService`, `*Requirement`, `*AuthorizationHandler` or `*ClaimsService`, an AutoMapper resolver or profile, and the gate helpers' own bodies. Each hub carrying `[Authorize]` is one more gate, its connection. `NOTE` lines, never failures, list `[AllowAnonymous]` routes, handlers whose `Authorize` returns `true`, and gates no route, hub or caller reaches (latent). Since 2026-10-09 also: a call to a class's own `Can*` helper that asks the authorization service (vm.api's `VmService.CanViewMapAsync`, caster.api's `FileCommandHandler.CanLock`), without a receiver or on `this`/`base`, from the same type or one deriving from it (a domain method that asks no service, caster.api's `File.CanLock`, is not one); the authorization calls inside a selector helper (cite.api's `SubmissionService.HasSpecificPermission`), each a sub-gate reached only by the call sites that pass a `SpecificPermission` value leading to it; the scope requirement of the default policy and of a global MVC `AuthorizeFilter`, one gate per member that builds it; and each mapped hub's connection, from its `MapHub<T>`: the hub class's `[Authorize]`, or `.RequireAuthorization()` on the mapping. Type names resolve by namespace (the same namespace, the file's `using`s, an enclosing namespace), so two features' `BaseHandler`s are two types, and a hub class no `MapHub` maps is `NOTE unrouted` with its methods (vm.api's `Hubs/VmHub.cs`). Parameters are read from the signature, not the attributes above it. `NOTE uninventoried` lines list members that throw `ForbiddenException` with no call the check inventories (a data gate, a claims read such as `GetAuthorizedViewIds().Contains(...)`): the reviewer reads those by hand.
   - **Gate ids.** `<path from the repo root>#<Type>.<Member>`: `<Request>.Handler.Authorize` for a handler, `@2` for a member's second overload, `:3` for the third call site in one member (each call site is its own gate: a two-tier gate is two), `#<Hub>[Authorize]` for a hub's connection (`#<Hub>[RequireAuthorization]` where its mapping gates it), `#<Type>.<Member>[scope]` for a scope requirement. The check prints them; the allow-list and `// Gate:` use them.
   - **Which tests reach a gate.** A test case is a `[Fact]`, or one row of a `[Theory]` (an `[InlineData]` row, or a row of the string table a `[MemberData]` names, as in blueprint.api's `RouteAuthorizationTests`). The case's text includes the private helpers of its class it calls, three levels deep. It reaches a gate by any of:
     1. **Its request.** The verb and url of an `HttpClient` call or an `HttpRequestMessage`, read from a literal or interpolated string, a `const`, a theory row, an expression-bodied helper (`UserRoute(id) => $"{Users}/{id}"`), or, when the url passes through a helper's parameter, the route literals and constants the case mentions. The url is matched against the gate's routes: a controller's `[Route]` with the action's `[Http*]`; a minimal-API `Map*` under its `MapGroup`; the controller actions that send a MediatR request, or call a service method; the most specific route wins, and a route with no gate still competes (`api/permissions/mine` is not `api/permissions/{id}`). A url built by concatenation or with `.Replace(...)`, or by a helper or property whose body holds exactly one route literal, resolves too. A case with a request the check cannot resolve is linked by its name as well as by its other requests.
     2. **Its name, when it sends no request** (a service, hub or handler test). The class name starts with a stem of the gate (`FileService`, `File`, the hub's name, the feature folder: `ViewRequestTests` for `Features/Views`) and either the method name's leading word, up to the first `_`, is the operation (`Edit_`, `UploadAsync_`, `JoinView_`) or the case calls the member. A call named like an `HttpClient` method (`GetAsync`) links only on a receiver that is not a client.
     3. **A link.** `// Gate: <id>` on a line of its own inside the test, for a test the first two cannot link (a class named for something else). A link says which gate the test is about; it does not make a test count that holds the wrong grant.
   - **The allowed case**, per call site: not a denial; the caller is not `Root` (`RootClient`, `Client(Root)`, `WithAllSystemPermissions()`, a helper that falls back to `Root` such as `HostFor(user ?? Root)`) and not anonymous; and it holds one of the call site's permissions, written in the case (`ViewPermission.ManageView`, `AppTeamPermission.ControlTeamVms`, `"ManageView"` in a theory row). For a resource permission, a membership step that names the role carrying it counts too (`InGroup(group.Id, GroupMembershipRole.Manager)`, `OnMsel(msel, MselRole.Owner)`), and so does the membership step itself where the app's `TestActor` has no parameter for that permission's enum (gallery.api's `OnTeam`: membership is the grant). A gate that names no permission (a requirement's `IsMet`, a data gate, `CanAccessVm`) takes any non-`Root` caller with a grant or a data row. cite.api's `SpecificPermission` selects which team permission `HasSpecificPermission` asks for; it is not a permission a test grants, so those gates name none. Not a case that answers 5xx (`InternalServerError`, `Status500InternalServerError`, a name saying `server_error` or `Is500`): a gate whose every admitted caller gets a 500 is allow-listed (`Defect:`, below). Where an earlier call site of the member short-circuits this one (`!a && !b` before a throw, `a || b`, an `else if`, a flag both feed), not a case holding the earlier site's permission, which never reaches this one; where both must admit (`!a || !b`, `if (!a) throw; if (!b) throw;`), holding both is right. `--covered` names the case holding the fewest permissions, then one per permission the site accepts.
   - **The near-miss denied case**, per call site: the case asserts the denial (`HttpStatusCode.Forbidden`, `ForbiddenException`, `Status403Forbidden`, a literal 403; in a denial test with a control request, the statement holding the denied request or its response variable, so the control is not read as denied; in a service or hub test that answers without a status, a name that says so, `_is_forbidden_`, `_refuses_a_caller_`, `_does_not_let_a_caller_`, `_leaves_out_`, or `DidNotReceive().AddToGroupAsync`), and its caller holds a grant or the case carries `// Data-row gate:`. An empty-grant denial does not count, a seeded id (`TestData.Permissions.CreateViews`) is no grant, and neither `Root` (nor an actor holding every system permission that all the case's requests use) nor a scope test (`TestAuthHandler.ScopeHeader`) is a near miss. The refusal must be able to come from this call site: a denial on a route that passes an earlier gate first (a controller's own check before the service's, a handler's `Authorize` before its `HandleRequest`, an earlier refusing site of the member that must also admit) counts only if the caller holds a permission of that earlier gate; in a short-circuit chain every denial is a denial at each site, so the caller must hold a permission of this site's family (one of its enums: another value, or the same one on another resource), which gives the evaluation tier and the team tier a near miss each; a site inside a loop takes only a test that names it with `// Gate: <id>` once the writer has made sure the test enters the loop (player.api's `Users/Get.cs:74` was credited with a user on no team); a `_does_not_let_a_caller_` test that asserts the caller was let in (`Assert.True(...WasSuccess)`) is no denial, and a Leave method's test is no denial by what it does not join. **Branch gates.** A site's verdict can decide a refusal (an `if` that throws or forbids, a handler's `Authorize`, a returned verdict), pick a branch (passed to a call, read in an `if` that refuses nobody, combined into a flag), or both (cite.api's `viewAsAdmin`: in the refusal condition and passed to the service). A site that picks a branch also takes, as its near miss, the other branch: a granted caller holding none of the site's permissions, answered 2xx, and none of the permissions of the sites its verdict is combined with (unless the verdict is also read alone); for a site naming no permission, a test named for what the branch leaves out (`_leaves_out_`, `_only_`, `_masks_`); and a service or hub test refused without a status. A site that only picks a branch takes no 403 as its near miss: the 403 on its route comes from another gate.
   - **A hub's connection**: an allowed case connects with `HubConnectionBuilder` and an identity; a denied case is refused without one (the connection throws, or the negotiate request is a 401). The allowed caller is an `Actor()`, never `Root`.
   - **The allow-list**, `/mnt/data/crucible/agent-docs/api-test-gaps/<app>.txt`, for what the harness genuinely cannot reach. It lives outside every repo, like the defect documents; the check finds it by the app name (`--app` in `verify.sh`, as for `defects`), reads no other list, and fails a test project that holds an `untested-gates.txt`, so none is committed by habit. One line per gate, `<gate id> Reason: <why>`; a member's id covers its call sites. A reason names what stops the harness, not the writer: a hypervisor no in-process host reaches; a near miss that can only be characterized as a defect (the gate answers the near miss with a 500, or admits it); an allowed case that can only be characterized as a defect (an inverted gate that refuses every caller holding its permission; a gate whose every admitted caller gets a 500); or an inert verdict no caller can observe (computed and never read; or read only on a branch no admitted caller reaches, player.api's `GetByUserView`), each naming the defect entry's test or the production `file:line`. A defect path the harness can still drive to a 2xx (a client-chosen id) is no such reason. A reason starting `Inert:`, or naming an entry or "Needs a decision" item of the app's defect document by its test name (a reason starting `Defect:` must name one, or the check warns), stands even where the check credits tests: the gate counts as allow-listed and prints `ALLOWED`, and `--covered` prints a `LISTED` line with what it credited. Any other listed gate the check covers prints a NOTE, `is covered now; delete its allow-list line`, and an id it no longer inventories a `stale` NOTE. The check fails (`ALLOW`) a line with no reason, and a reason about budget, time, a follow-up, a later or next round, or scope: such a line hides a missing gate. Every allow-listed gate is printed as `ALLOWED`. The list is not in the PR, so the PR body names each listed gate with its reason (`deliver.sh` writes it; ../testing/README.md, "Delivery").
   - **Provisional gates** ([GLOSSARY.md](../GLOSSARY.md)). A shape a standard version inventories for the first time, or a credit it stops accepting, that leaves a gate uncovered prints `WARN provisional: ...` with the reason for that one version and counts as `provisional` in the summary, `(gates: N call sites in M members, C covered, A allow-listed, X missing, P provisional)`; from the next version it is a `GATE missing:` line. The 2026-10-09 shapes and refused credits (an allowed case answering 5xx, a `Root` or scope near miss, a refusal from an earlier gate, a loop site, a near miss outside the site's family) are missing gates from 2026-10-12, and their `GATE` lines say so. For ready a provisional gate counts like a missing one: covered, linked with `// Gate:`, or allow-listed.
   - **What it cannot see.** It reads text: it cannot tell which branch an admitted caller took (player.api's caller asking about itself never reaches `GetByUserView`'s `else if`; an `Inert:` line says so), whether a loop ran, or a near miss that holds too much (the default-role pitfall above). `check-repo.js gates <repo> <app> --covered` prints, for each covered gate, the allowed and near-miss tests it credited (and, for a site with a system tier and a resource tier, `tiers: system <case>, resource <case>`, so each path that grants shows its own near miss); the reviewer reads them.

2. **Persistence, read back through a cold context.** What a write stored (and did not store: a rolled-back failure leaves the row as it was), read through `NewContext()`. Include the cascade and uniqueness behaviour the real schema enforces; that is what the PostgreSQL harness is for.
3. **Entity events and hub broadcasts, through recorders.** A write's entity event reaches the real handler, and the handler's broadcast reaches the right group with the right payload: `Factory.Hub<THub>().ToGroup(id)` in a run-wide host (a `Clients.Groups(list)` send is recorded for each group in it, and `ToGroups(a, b)` reads the call itself), the `HubRecorder` of a per-class factory, `Mediator.Received()` on a test's own context. Hub methods themselves with `HubHarness` (which groups a connection joins and leaves, `JoinedGroups`/`LeftGroups`, and what the caller and each group is sent), the caller a `ClaimsPrincipalBuilder` principal read by the real authorization service (section 1).
4. **Exception middleware and filter shapes.** Each exception type the app maps (forbidden, not found, conflict, bad request, an unhandled one) produces the status and body clients parse: `application/problem+json` through `AssertProblem`, or an MVC `JsonExceptionFilter`'s `application/json` body through `AssertJsonError` (`AssertJsonError<TError>` for an app's own error type); both return the body so the test asserts its `Detail`. The unhandled-exception case needs a defect as its vehicle (section 3, "A shape test needs a vehicle"). Malformed bodies, malformed route values and out-of-range enums at the edge.
5. **Services and background services** driven directly: options a test chose (`ServiceTestBase`), outbound HTTP through `StubHttpMessageHandler`, logs through `RecordingLogger`.
6. **Mapping, converters, extensions** and other pure helpers, without the harness. `TestMapper` over the real AutoMapper configuration; `AssertConfigurationIsValid` where the profiles allow it.

## 5. The broken-gate check

`verify.sh` cannot do this one. Pick an authorization gate the tests claim to cover and break it **at the call site of that one endpoint** (the `Authorize(...)` override of that handler, the permission list passed to the authorization service in that controller action or service method) so it always allows. Breaking it inside the authorization service, a requirement handler or the claims transformer breaks every gate at once, and any test failing proves nothing about this gate.

**The edit.** Keep the collaborator referenced: under `TreatWarningsAsErrors` an unread primary-constructor parameter is error CS9113, so `=> true` does not build. Two forms build, and they differ in whether the check still runs:

- `await authorizationService.Authorize([...], ...) || true` runs the check and discards its verdict. Use it when the path after the gate depends on something the check does on the way, which is rare.
- `true || await authorizationService.Authorize([...], ...)` never runs the check. The reference keeps CS9113 quiet, and the compiler reports nothing for the short-circuited operand. Use it whenever the check itself can throw for the denied actor, and when in doubt. With `|| true` the throw comes before `|| true` is reached, so the gate never opens, and a denied test that characterizes the throw keeps passing for a reason that has nothing to do with the gate. player.api's example is `FileService.GetAsync` (`FileService.cs:103`): `Authorize(SystemPermission[], ...)` throws `ArgumentNullException` for a team member without the system permission, the null-array defect.

Mind the negation. A gate written `if (!await authorizationService.Authorize(...)) throw ...;` becomes `if (!(true || await authorizationService.Authorize(...)))` (or `!(await ... || true)`). Appending ` || true` inside the `if` parses as `(!await ...) || true`, which builds and refuses every caller: the allowed tests fail, the denied tests pass, and the run reads as a gate the tests do not cover.

**Other shapes of gate.** Break the operand that decides, and only that one:

- **A two-tier gate** (a system permission, or else a resource requirement): `if (!hasSystemPermission && !await XRequirement.IsMet(...)) throw ...;` becomes `if (!hasSystemPermission && !(true || await XRequirement.IsMet(...)))`. The denied test's actor lacks the system permission, so the resource tier is the gate under test; breaking `hasSystemPermission` instead (`true || hasSystemPermission`) opens the other tier, and a denied test failing then is about that tier.
- **A gate assigned to a variable** that a later line or a service reads: `var hasPermission = await authorizationService.AuthorizeAsync(...);` becomes `var hasPermission = true || await authorizationService.AuthorizeAsync(...);` (cite.api's `MoveController.cs:65`). Break it where it is assigned, not where it is read, and break every read that re-checks it.
- **A data gate**, a condition on a row rather than a permission (an `isRequired` flag, an invitation's expiry, a `CreatedBy` match): `if (isRequired && !matches) throw ...;` becomes `if (false && isRequired && !matches)`, which keeps every operand referenced. Its denied tests carry the `// Data-row gate:` comment (section 4) or seed the actor's id into the row.
- **A gate in a hub method** is broken the same way at its call in the hub; the denied `HubHarness` test fails because the method now joins the group or sends.
- **An inverted gate**, which throws when the check admits (`if (await X) throw ...;`), has no `!` to work around: it becomes `if (false && await X)`.
- **A hub gated by its mapping** (vm.api's `MapHub<VmHub>(...).RequireAuthorization()`): replace `.RequireAuthorization()` with `.AllowAnonymous()` on that one mapping; the hub's refused-connection test fails because the connection now opens.
- **The scope requirement** is checked twice in the MVC apps (alloy.api, blueprint.api, cite.api, gallery.api, steamfitter.api): the default policy (`AuthorizationPolicyExtension`, `RequireClaim("scope", ...)`) and a global `AuthorizeFilter` built in `Startup` with `RequireScope`. For a controller route, break both copies, as for any repeated check below; the filter does not apply to hubs, so a hub's scope test breaks with the policy alone.

**Repeated checks.** When one path checks the same gate more than once, break every copy on the path in the same edit. With one copy broken the other still refuses, so the denied test passes whether or not the tests cover the gate, and breaking one copy proves nothing. player.api's upload is the example: `FileService.UploadAsync` checks `ManageView` at `FileService.cs:71`, and the private `uploadFile` it calls checks it again at `:326`. Before the edit, find the copies by reading the path from the endpoint down: the handler, the service method, and the private helpers it calls (grep the permission name). In the report, say that the check repeats and list each `file:line` broken. A repeated check is not a defect in itself and gets no entry.

**Run and restore.** `../testing/break-gate.sh` makes the edit (`--site <file>:<line> --replace <old> <new>`, every copy of a repeated check in one run), builds, runs the near misses, restores the file byte for byte, rebuilds, and logs the result (../testing/README.md, "The broken-gate check"). Read each near miss's failure line: it fails because the request now got through (the allowed status, a stored row), not with a new exception. A gate whose near miss still passes when broken is a blocker.

**Who runs it.** The writer runs it on every gate it covered, and on each gate the reviewer names. The reviewer reads the log, and names an extra gate (every call site on the path, the edit, the near misses expected to fail) only when the selection is weak: a gate in scope whose credited tests changed has no run, or a gate shape in scope (two-tier, assigned to a variable, data-row, hub) is not represented.

## 6. Review criteria beyond the rules above

What the reviewer asks of every test, in addition to sections 1 to 5:

- **Is every "Found without a test" reason one the harness cannot meet?** An item the harness could characterize as written, or an instance of a recurring pattern whose siblings are entries, is a should-fix: it becomes an entry with its test.
- **Does a denial test's control request stay one control?** (section 1, "One Act per test").
- **Does every gate the check credits hold?** `check-repo.js gates --covered` names the allowed and near-miss test for each covered gate; one that does not test what the credit says (a near miss holding too much, a branch credit for a caller that takes an earlier branch) is a blocker: the gate counts as missing until it is fixed. A `WARN provisional:` line blocks ready like a missing gate.
- **Does every allow-list reason hold?** A reason in `agent-docs/api-test-gaps/<app>.txt` the harness could meet hides a missing test: a blocker, like the missing gate it covers. A reason that misdescribes a gate the tests do cover (cite.api's first `GetForScoringModel:1` line, written when the check could not credit a branch gate) is a should-fix: correct the reason or delete the line. Read every `LISTED` line: a gate the check credits stays allow-listed only while the `Inert:` or `Defect:` reason is true.

- **What would have to break in production for this to fail?** A test that only asserts a substitute was called where an observable outcome (a status, a stored row, a recorded broadcast) was available; a test whose stub returns X and that checks X came back through nothing; a test that asserts on the seeded object rather than a cold read: each is a tautology.
- **Is the real thing under test?** A substituted authorization service, mapper, mediator handler or context where the real one would run hides the code under test.
- **Is the host shared?** An assertion on a run-wide surface not keyed to the test (section 2, common mistakes).
- **Is the database real?** No EF InMemory, no SQLite, no hand-built `DbSet` (`verify.sh` fails the first two).
- **Is every defect entered once, and only in the document?** (section 3).
