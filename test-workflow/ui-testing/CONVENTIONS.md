# Conventions for Crucible UI specs

How specs are written in every Crucible UI. `angular-test-writer` follows this file and `ui-test-reviewer` reviews against it, so a rule that is not here, in [../orchestration/RULES.md](../orchestration/RULES.md) or in the formats of [../testing/README.md](../testing/README.md), is not a review criterion; section 6 holds the reviewer's questions beyond the rules. Only `test-standard-maintainer` edits it, at a standard version; changes are listed in [CHANGELOG.md](CHANGELOG.md). The setup itself (builders, zone, helpers) is in [README.md](README.md) and [SETUP.md](SETUP.md).

## 1. Akita: how to test it

These rules come from Akita 8.0.1's source and from the eight Crucible migrations.

- **Loading.** Akita ships bundler-only ESM. Without the patch, any spec that imports `@datorama/akita` (directly or through a store, query, service or `@cmusei/crucible-common`) fails at import time.
- **Use real state. Stub the edges.** For a feature's `state/` or `data/` folder (store + query + service), test with the **real** store and query and stub the generated API services the data service calls, plus SignalR. Assert on the query's output, not on internal store calls.
- **What counts as state.** Akita stores, queries and data services, and non-Akita services that hold app state in `BehaviorSubject`s (player.ui's and vm.ui's data services). They stay real in component specs too. A service that wraps an external runtime rather than holding state (a hub connection, the WMKS console, a browser API) is an edge: component specs stub it with a typed `Pick<>`, and its own spec covers it against a fake of the runtime. A state service provided by an NgModule or component rather than `providedIn: 'root'` is listed in `getDefaultProviders` as its real class.
- **Router-reading data services.** A data service whose constructor reads router state is an `unstubbed()` placeholder in the defaults. Its own spec uses the real service under `RouterTestingHarness`. Component specs pass a typed stub (`satisfies Pick<XDataService, ...>`) that returns only what the component reads, and assert every call the component makes on it at least once.
- **Isolation.** Stores are `@Injectable({ providedIn: 'root' })`, and TestBed builds a new root injector per test, so each test gets a fresh store. Don't rely on `resetStores()` or `store.reset()`; they only work for `resettable: true`, which no Crucible app sets. Akita keeps a global `__stores__` registry by name and a new instance overwrites the old one; never hold a store across tests. For a pure store/query test you can skip TestBed: `const store = new XStore(); const query = new XQuery(store);` (check constructor arguments).
- **Dev mode.** `@StoreConfig({ name })` is required; Akita asserts it in dev mode, and tests run in dev mode because `enableAkitaProdMode()` lives in `main.ts`. Don't call it in tests. Dev mode also **deep-freezes stored entities**, and several data services mutate API responses (`setAsDates`, sorting). Return a fresh object per stubbed call: `vi.fn(() => of(structuredClone(fixture)))`. A frozen fixture reused across calls throws, which is a fixture problem, not an app bug.
- **`persistState` doesn't run in tests** (it lives in `main.ts`). Code that reads `localStorage` directly still might, so call `localStorage.clear()` in `beforeEach` where relevant.
- **Observables.** `query.select*()` emits the current value synchronously on subscribe, then on change, with `distinctUntilChanged`. Use `recordEmissions(query.selectAll())` for sequences or `firstValueFrom(...)` for one value. Akita updates are synchronous; don't add timers. Updates inside `applyTransaction` emit once. The exception is `combineQueries(...)`, which pipes `combineLatest` through `auditTime(0)` (Akita 8.0.1 `combineQueries.js`): a component built on it renders its rows only after `await fixture.whenStable()` (or `await flush()` in a service spec).
- **Entity UI stores.** Stores that call `createUIStore()` keep per-entity UI state in `store.ui`, seeded by `setInitialEntityState`. Assert through `query.ui.selectEntity(id)` and test that new entities get the initial UI state.
- **Akita in components.** Prefer a real store and query seeded with `store.set([...])` over a hand-written query stub. Stub only `RouterQuery` (`select`, `selectQueryParams`, `getParams`).
- **Seeding a store before the component is built.** A component that reads a root store in its constructor or a field initializer (`selectActive()`) needs the store seeded before `render`. `TestBed.inject(XStore)` before `render` throws "Cannot configure the test module when the test module has already been instantiated"; pass `provideEnvironmentInitializer(() => inject(XStore).set([...]))` in the render's `providers` instead.
- **`ComnAuthQuery`** from `@cmusei/crucible-common` is an Akita query. Stub it (`userTheme$`, `isLoggedIn$`); don't construct the library's stores.

## 2. Conventions every spec follows

- **License header** on every new file:

  ```ts
  // Copyright <current year> Carnegie Mellon University. All Rights Reserved.
  // Released under a MIT (SEI)-style license. See LICENSE.md in the project root for license information.
  ```

- **Imports.** `import { describe, it, expect, vi, beforeEach } from 'vitest';`. No Jasmine (`jasmine.createSpy`, global `spyOn`, `toHaveBeenCalledOnceWith`).
- **Components.** Render with `renderComponent(Component, { ... })`. Write a local `renderX(overrides = {})` factory that returns the render result plus the spies the tests need. Child stubs are minimal `@Component({ selector, template: '' })` classes with the same inputs and outputs. On Angular 21 `@Component` defaults to standalone, so a stub goes in `imports`; to pass it in `declarations` (NgModule apps) it needs `standalone: false`. Standalone apps swap children with `childStubs: [{ replace, with }]`.
- **Child stubs prove inputs, not text.** A stubbed child renders nothing, so an assertion on text the real child would render proves nothing. Query the stub instance (`fixture.debugElement.query(By.directive(ChildStub)).componentInstance`) and assert its inputs. Every `*$` gate the component passes to a child stub (`[canEdit]="canEdit$ | async"`) gets an allowed and a denied assertion on that input.
- **Typed stubs, no `any`.** Generated API services: `const xApi = { getX: vi.fn(() => of([...])) } satisfies ApiStub<XService>;`, with literal keys. Table-driven rows that name the endpoint use `endpointStub(XService, endpoint, fn)`; never a computed key (`{ [endpoint]: fn }` widens to an index signature and checks nothing). A member whose generated type is wrong sits next to a spread checked block, typed to what the API sends, under a plain comment naming the API endpoint, with a typing-note entry in the app's defect document (section 3; see `api-stub.ts`). App services, and common-library services a spec overrides in part (`ComnAuthService` with only `user$`): `Pick<RealService, 'a' | 'b'>`, cast once. `vi.fn(() => of(...))` for observable methods; `EMPTY` or `NEVER` to keep a subscription inert, with a comment saying why. `verify.sh` fails a generated-service stub that is not checked against `ApiStub`.
- **Router stubs.** `activatedRouteStub()` (`activated-route.ts`) is the ActivatedRoute stub; no hand-written route objects. A Router stub is typed: `{ provide: Router, useValue: { navigate } satisfies Pick<Router, 'navigate'> }`, adding only the members the code calls. Code that reads router state (`routerState`, `url`, `events`) runs against a real router (`provideRouter` + `RouterTestingHarness`).
- **Placeholders.** Defaults come from `getDefaultProviders`. Pass a stub only for what the code under test uses. An `unstubbed()` placeholder throws a message naming the missing member; add exactly that member. Don't make placeholders permissive to silence errors. A dependency that is injected but unused is `unstubbed(X)`, never `{ provide: X, useValue: {} }` (`verify.sh` fails that).
- **Dialogs.** `dialogRefStub<T, R>(result)` for a dialog that closes with a value, `dismissedDialogRefStub<T, R>()` for one the user dismissed (`afterClosed()` emits `undefined`, then completes), `dialogRefStub<T>()` for a dialog whose `afterClosed()` should stay silent. Escape handling is driven through the returned `keydown` subject. No hand-rolled dialog refs. A host that reads the opened dialog's instance (`dialogRef.componentInstance.editComplete.subscribe(...)`) gets it by assignment on the stub's ref: `dialogRef.componentInstance = { editComplete } as Pick<X, 'editComplete'> as X;`, one cast, with only the members the host reads (cite.ui's `matDialogStub` in `mat-dialog.ts` is the allowed app-specific form of the same thing).
- **Services that open a Material overlay** (a `MatDialog`, `MatBottomSheet` or snack bar opened from a service) are tested with the real overlay, never a stubbed `open`: the real service, the real `MatDialog`/`MatBottomSheet` from the root injector, `provideNoopAnimations()` (or `NoopAnimationsModule`), and assertions on what renders (`await screen.findByRole('dialog')`, its title and text, the button that closes it). The opened component is used as the app compiled it: the unit-test build is AOT, so a `standalone: false` component already carries the template scope of its NgModule and opens without being declared in the TestBed (importing the app NgModule does not help: in the test build its `ɵmod` lists no declarations or exports). Declare it with its Material modules in `TestBed` only if the AOT scope does not resolve, with a comment saying so.
- **Queries.** Testing Library queries in priority order: `getByRole`, `getByLabelText`, `getByText`, `getByTestId` last. Interactions through `@testing-library/user-event` (`const user = userEvent.setup()`). jest-dom matchers (`toBeInTheDocument`, `toBeDisabled`, `toHaveTextContent`). Material harnesses when a widget's DOM is awkward, but note that a harness waits for stability and hangs on a component with a running `setInterval` or `interval()`; read the DOM directly there. In large Material templates scope role queries with `within(...)` (README, "Testing Library with Material in jsdom"). The stock queries are the standard: shared helpers that replace them (role-by-selector plus text matching, key-press wrappers) were rejected by the user on 2026-10-09.
  - **Icon buttons named by `title`.** `getByRole('button', { name: 'Delete' })` finds a button whose only name is its `title` (the title is the accessible name), so that is the query. A `within(...)`-scoped `getByTitle` is allowed where the role query's cost dominates a test under coverage; it does not filter hidden elements, so never use it for an absence check or on content inside a collapsed panel.
  - **Tooltip descriptions.** `matTooltip` text is the control's accessible description, set in a microtask: `getByRole('button', { description })` after `await fixture.whenStable()`. A denied case that queries by description has an allowed case that finds the same element with the identical query and render path, or it queries by `title`; otherwise a description that is simply missing would pass the denied case.
  - **Disabled controls.** A denied case asserts state: `toBeDisabled()` (or the control's own `.disabled` property, see below), never "clicked it and nothing was called". A disabled Material button has `pointer-events: none`, so user-event refuses the click and the `not.toHaveBeenCalled()` after it proves nothing. jest-dom's `toBeDisabled`/`toBeEnabled` treat a custom element carrying a static `disabled` attribute (`<mat-expansion-panel disabled>`, `<mat-checkbox disabled>`) as disabling every descendant, so a denied assertion on a button inside one passes whatever the gate does: assert the control's own `.disabled` property there (`expect(button.disabled).toBe(true)`). `mat-select` reflects its state only as `aria-disabled`.
  - **user-event's pointer check.** `userEvent.setup({ pointerEventsCheck: PointerEventsCheckLevel.Never })` is allowed in a spec whose clicks are measured to cost seconds under coverage, set once per spec file with a comment giving the measurement. user-event still refuses disabled targets with it, but it clicks through `pointer-events: none`, so denied cases in that spec assert state as above. For a text field, `field.focus(); await user.type(field, text, { skipClick: true })` avoids the check without the setting; for a checkbox or toggle, focus it and `await user.keyboard(' ')`.
- **Async.** `await fixture.whenStable()`, `fixture.detectChanges()`, `await flush()` from `unhandled-rx-errors.ts`, or a Testing Library `findBy*` query (it waits for the DOM, and is the natural wait in a service spec that has no fixture, such as an overlay opened by `MatBottomSheet`). No `fakeAsync`. `vi.useFakeTimers()` only for real timer logic (polling, backoff, debounce), restored afterwards. A service that defers its `open()` with `setTimeout` is called inside `TestBed.inject(NgZone).run(() => service.show(...))`, where the app's callers run it, and then awaited with `await TestBed.inject(ApplicationRef).whenStable()` or `findBy*`; called from the test body, outside Angular's zone, `whenStable()` does not wait for the timer, the overlay opens after teardown, and Vitest reports NG0205 "Injector has already been destroyed". No fake timers for this.
- **Change detection.** Tests run with zone, like the app, but the fixture does not auto-detect. Re-render through Testing Library events (`user.click`, `user.upload`, `fireEvent`) first, and `fixture.detectChanges()` after state the test changed itself. Never call `markForCheck()` on the component from a test; if an OnPush component won't update, drive it through its UI instead of patching its state.
- **Console errors fail tests.** `test-setup.ts` fails any test that logs `console.error`, which is how zone.js surfaces an unhandled rejection outside Angular's zone (one inside it, like a throw in a subscribe there, is rethrown by TestBed instead). A test that expects a logged error opts out with `vi.spyOn(console, 'error').mockImplementation(() => {})`, or with `captureUnhandledRejections()` when the error is an unhandled rejection; either way it asserts on the whole list of logged errors (`toEqual([...])`), so an unrelated one still fails it. A Vitest summary with an `Errors` line (`Errors  1 error`) while every test passed is a failure of the test Vitest names under "This error originated in ..." ("The latest test that might've caused the error is ..."); fix it, never treat it as a flake. An error thrown in a parent's listener for a child's `output()` is logged twice (the rethrow is caught by `OutputEmitterRef.emit` and reported again), so a test that asserts the whole list sees two entries where the app reports one.
- **SignalR.** Never open real connections. `mockHubConnectionBuilder()` in `beforeEach`, then `connections[0].trigger('EventName', payload)`. Stub hub results with `invoke.mockImplementation` keyed on the method name. To pin a missing `.catch` on a hub call, `rejectInvokes(hub, error)` plus `captureUnhandledRejections()`. Never spy on `HubConnectionBuilder.prototype` from a spec; `onBuild` and `connections` cover it (`verify.sh` fails it).
- **Hub payloads come from the API.** Trigger a hub event with the payload the API's SignalR handler actually sends (read `<app>.api/.../*SignalRHandler.cs` or the hub's `SendAsync` calls in the workspace), not the type the UI handler is annotated with. Where they differ, the spec pins what the UI does with the real payload and, if that is wrong, the defect document gets a cross-repo entry that names the API file and line (section 3).
- **Lifecycle hooks that throw.** When a pinned defect makes a hook throw (an `ngOnDestroy` that calls `complete()` on a subject it already unsubscribed), TestBed teardown fails every other test of that component. The other tests stub that hook with `vi.spyOn(X.prototype, 'ngOnDestroy').mockImplementation(() => {})` in their `beforeEach`, under a plain comment naming the pinned test; `restoreMocks` restores it, and the spy is removed with the fix. The pinned test itself runs the real hook.
- **Pinned NG0100.** A component that a pinned defect makes throw NG0100 ("Expression has changed after it was checked") is rendered with `detectChangesOnRender: false` and then `fixture.detectChanges(false)` (change detection without the check-no-changes pass), only in the tests that need to render past it, with a plain comment naming the pinned test.
- **HTTP.** Stub the generated API services. `provideHttpClient()` + `provideHttpClientTesting()` only when the service under test builds HTTP requests itself.
- **Permissions.** `permissionDataProviders(grants)` for gate tests. Cover allowed and denied for each gate, plus system, team and resource precedence where the app has them.
  - **Denied cases are near misses.** The denied grant carries a permission close to the required one (another permission on the same resource, the same permission on another resource or scope, View where Edit is required), never an empty grant list. An empty grant cannot tell a broken claim filter from a working one; that is how broken gates passed in player.ui and vm.ui.
  - **Gated actions go through the UI.** Trigger a gated action the way the user does (click the rendered button, open the rendered menu), and assert that the control is absent or disabled when denied. Calling the component method directly skips the gate in the template. Setting up state through a third-party API that jsdom cannot drive is not a shortcut around the gate as long as the gated action is still clicked: `ngx-drag-to-select` has no layout to drag in jsdom, so a spec selects through the container's `selectAll()` and then clicks the gated button.
  - **A denied case per gate.** A file with several independent gates (a page with one section per permission, a toolbar with Edit, Delete and Import) needs a denied case for each, not one for the file: each gate's denied case renders the near miss for that gate and asserts that gate's control. `check-repo.js gates --list` prints, under each gated file, every gate and the denied test whose own text names it ("no denied test names it" is the reviewer's cue to look).
  - **Every permission value has an allowed render.** Coverage is counted per value: every permission value some gate accepts (system, view, team, MSEL, project, claim values) has at least one render, somewhere in the app's specs, whose grant is exactly that value and where the gated control shows, besides the near miss. A pattern gate (`startsWith('View')`, `endsWith('Events')`) additionally gets one render per pattern with a representative value. A value no UI code reads is reported under Untested as "unused in the UI".
  - **Inputs bound from a permission are gates of the child.** A child input fed from the parent's permission value under another name (`[showAdminButton]="canViewAdministration"`, `[readOnly]="!canEdit"`) is where the gated control lives, so the child's spec needs a denied case for it (the input at its denied value). `check-repo.js gates` fails each one without such a denied case (`DERIVED missing:`).
  - **Every gated file has a denied case.** `check-repo.js gates` (run by `verify.sh`) inventories every component, directive and guard under `src/app` that reads a permission: a `can*` name in the class or template (`canEdit`, `canEdit$ | async`, a `canEdit` input, `canEvent(...)`), a `*Permission.Member` value tested on a permissions list (`permissions.includes(SystemPermission.ViewUsers)`), or a call on the app's permission service (`hasPermission(...)`, `can(...)`, `permissions$`). The pattern table at the top of the check's gates section is the definition. Not gates: a `can*` method nothing calls, a `can*` field that is only ever a boolean literal and that no other code sets, and `can*` names that are only lambda parameters, destructured names or locals (the permission read on a local's right-hand side still counts). A gated file fails until the spec beside it has a test that both sets up permissions (`permissionDataProviders(...)`, a `PermissionGrants` value or key, a `*Permission.Member`, or the component's own gate name such as `canEdit: false`) and asserts something absent or disabled (`not.toBeInTheDocument()`, `toBeNull()` on a query, `toBeDisabled()`, `toBe(false)` on a stub input, `toEqual([])` on a rendered list, an `it.each` matrix of grants against the exact rendered list). When several tests qualify, `--list` names the one whose own text sets up the denial (a grant, the gate set false, a factory called with `false`) before one whose setup comes only from its factory or `beforeEach`, and that before one that matches only through a gate word elsewhere; a file whose only qualifying tests are of the last kind fails as `WEAKDENY missing:`. The check recognizes the shape, not the quality: whether the denied case is a near miss and whether it fails when its gate is broken stays with the reviewer and section 5. A missing gate blocks delivery (RULES, Test quality).
  - **The allow-list is for what the harness cannot render.** The allow-list lives outside every repo, like the defect documents: `/mnt/data/crucible/agent-docs/ui-test-gaps/<app>.json` (for example `caster.ui.json`; `check-repo.js gates --app <app>` reads it, and fails if a `gates.allow.json` exists anywhere under the repo's `src`, so none is committed by habit). It is an array of `{ "path": "src/app/.../x.component.ts", "reason": "..." }` entries; an entry with `"gates": ["canRename"]` excuses only the named gates (a `can*` name that is not a permission, if the check misreads one), an entry without `gates` excuses the whole file, including its smoke spec, so it is only for a file the test build cannot compile or the harness cannot render at all. The reason says what the harness cannot do (a browser API jsdom lacks, a third-party runtime that cannot load). Time and budget are never reasons: the check fails (`ALLOW`) an entry with no reason, one whose reason mentions budget, time or a follow-up, and one that names a gate it does not find; an entry whose path matches nothing is a `stale` NOTE. Allowed entries print as `NOTE allowed` lines. An allowed gate is still an untested gate: the PR description names every entry (file, gates, reason), which `deliver.sh` writes.
- **Every unit has a spec beside it.** Not only components: every `@Injectable` service, pipe, directive, guard, resolver and interceptor under `src/app` (`generated/` and `test-utils/` excluded), and every Akita query that declares selectors of its own, has `x.spec.ts` beside `x.ts`. A construction-only spec (`should be created`) is replaced by a behaviour spec of the same class at the same path, never deleted. Akita stores, and queries whose members only pass their arguments to Akita (`selectById(id) { return this.selectEntity(id); }`), are wiring and need none. A unit that is pure DI wiring (a re-export, a token holder) gets an allow-list entry whose reason says so. `check-repo.js gates` fails a unit without a spec (`NOSPEC missing:`).
- **One `it` per case.** Cases that differ only in data use `it.each` (one doc block above it covers every row) or separate `it`s. A `for` loop around `it` is allowed when `it.each` cannot express it, with the doc block directly above the `it` inside the loop. No `TestBed.resetTestingModule()` in the middle of a test to run a second case; a reset in `beforeEach` is fine.
- **Doc block** over every `it`, including `it.each` cases:

  ```ts
  /**
   * Verifies: <the behavior, in one sentence>.
   * Interacts with: <collaborators touched>.
   * Data: <the inputs and setup that matter>.
   */
  ```

- **Test names** state the behavior: `it('hides the Add button without CreateViews permission', ...)`.
- **Every component has a spec beside it.** `x.component.spec.ts` next to `x.component.ts`; `check-repo.js gates` fails a component without one (`NOSPEC`). An Angular CLI boilerplate spec ("should create") is **replaced** by the smoke spec, never deleted outright; a spec with real assertions is rewritten in the standard's style at the same path. The smoke spec, from `templates/component-smoke.spec.template.ts`, renders the component with `renderComponent` and the default test providers and asserts it mounts. It is the floor, not the finish: a component that reads a permission still needs its allowed and denied cases. The smoke test carries no behaviour assertions: it is the template's one test, and it counts as coverage of no behaviour and no gate. Behaviour goes in named tests with their own doc blocks, in the same file. A smoke spec of an NgModule component may pass `schemas: [CUSTOM_ELEMENTS_SCHEMA]` instead of declaring child stubs (an unknown child element is otherwise an NG0304 `console.error`, which fails the test); never `NO_ERRORS_SCHEMA`, which also hides unknown bindings on native elements. Specs with real assertions use child stubs as above.
- **No test is lost.** A change that renames, rewrites, merges or deletes a test (an `it`, an `it.each` row, a whole spec file) keeps every observable the old test asserted: every rendered value, count, ordering, emitted value, call path, exact result passed to `close()`. An assertion the old test made inside its fake handler or stub (the request method, the path, that every request matched a pattern, the call order) counts too, and the successor asserts it on the recorder. "Asserts the rendered outcome instead of a mock" never licenses asserting less. Every removed title is matched by `check-repo.js removed` (moved, renamed with an identical body, `it.each` rows merged) or gets one line in `/mnt/data/crucible/agent-docs/ui-test-bugs/<app>.removed-tests-<date>.md`, in the notation of [../testing/README.md](../testing/README.md), "Removed-test accounting" (`describe > title` is fine). Time, budget and "trivial" are never D reasons; `trackBy` helpers, CLI scaffold assertions on a `title` the component never had, and a behaviour jsdom cannot express (D naming its e2e home in crucible-tests) are the usual legitimate ones. A replacement that asserts less than the test it replaced is narrowed: restore the observable, or give the dropped observable its own D line. `verify.sh` fails an unaccounted removal. The reviewer reads every line the writer judged against the old spec (`git show <base>:<path>`).
- **Exclusions.** Don't test `src/app/generated/**`.

## 3. Defects: a test in the spec, the description in the document

- **Characterize, don't fix.** If the code under test has a defect, the spec pins the *current* behavior with an ordinary passing test, and the defect is described in the app's defect document, `/mnt/data/crucible/agent-docs/ui-test-bugs/<app>.md` (for example `vm.ui.md`), which sits outside every repo. Don't change production code unless the task says to. The test passes today and fails once the defect is fixed; the entry tells the fixer which test that is.
- **No defect notes in specs.** A spec carries no defect description and no word `BUG` in any comment (`check-repo.js specs`, run by `verify.sh`, fails it). The test name and doc block state the current behavior neutrally (`leaves loading stuck when the runs request fails`; "Verifies: ... (current behavior)"). A plain comment at the assertion may state the current behavior and point at the document, nothing more: no expected behavior, no fix, no "should", "wrong" or "never". Everything else goes in the entry.
- **The entry.** The format of an entry and of the document is in [../testing/README.md](../testing/README.md), "Defect documents": `### <test name>` under `## <spec path>`, the heading the exact string passed to `it` (for `it.each`, the template with its `%s` or `$method`), so `grep -F` finds the test, and ``Test: `<spec path>` `<test name>` ``. A plain comment at the pinning assertion may state the current behavior and point at the document.
- **Cross-repo.** A fix that needs an API change (a payload, an attribute, a wrong OpenAPI type) is `Cross-repo; <api repo> first.`, naming the API file and line and what the UI must do so the corrected payload doesn't break it (accept both payloads, or ship together). Section 2 says which payload a hub test uses.
- **The same defect in another test.** Another test that touches a defect with an entry gets no entry of its own; at most a plain comment naming the test that has one (`// Same case as 'leaves loading stuck when the runs request fails' in run-data.service.spec.ts.`).
- **Recurring patterns.** Pin every instance, grouped: one `it.each` per service file and pattern, one row per affected method, and one entry for that `it.each` that lists each method with its production `file:line`. When several files share the fix, the document's recipe gives it once and each entry's `**Fix:**` names the recipe.
- **Latent instances** are pinned and entered like any other, with the latent marker of the shared format: `(latent: no caller)` when nothing in `src/app` calls the defective method today, `(latent: unreachable input)` when it has a caller but the defective branch cannot be reached from it (say which condition blocks it).
- **Fixtures that survive the fix.** When a pinned defect's fix will change what a shared factory or default grant yields (a role that wrongly grants Edit today), the other tests that use that default get a grant that gives the same result before and after the fix, so the fix flips only the test named in **Test to flip:**.
- **Gate defects with several endpoints.** When one page calls endpoints with different `[Authorize]` requirements (a view editor that saves the view, its teams and its files), a gate-type entry lists each endpoint with its own requirement and the UI gate it should map to, one line per requirement, instead of one flag for the page.
- **Wrong generated types.** A stub member typed to what the API sends instead of its generated type (section 2) gets a plain comment naming the API endpoint, and an entry `### (typing note on <stub>, not a test)` whose `Test:` line names the spec file. It is cross-repo: the OpenAPI document is fixed in the API, then the client is regenerated.
- **`subscribe()` with no error callback** is a defect when a loading flag or spinner stays set after the failure, or when the error escapes and the app has no global `ErrorHandler` that shows it. Check `app.module.ts` / `app.config.ts` for `{ provide: ErrorHandler, useClass: ... }`: a class that implements `ErrorHandler` but is never provided does not count (steamfitter.ui's `ErrorService`). caster.ui provides one, so there only a stuck loading flag is a defect; pin the escape anyway, with a plain comment naming the handler, and enter only the loading flag. Canonical form, the spec:

  ```ts
  /**
   * Verifies: a failed load leaves loading set and lets the error escape (current behavior).
   * Interacts with: RunsService.getRuns (throws), real RunQuery, captureUnhandledRxErrors.
   * Data: getRuns fails with a 500.
   */
  ```

- **Needs a decision.** An entry whose fix is a product choice (a dead gate: wire it or delete it) goes under `## Needs a decision` in the shared item shape, naming per option the test to add, flip or delete. Analysis of API behaviour (what an endpoint authorizes, what a hub sends) belongs in `## Gaps noticed`, never in a spec comment.
- **What the script checks.** `check-repo.js specs` (run by `verify.sh`) fails `BUG` in a spec comment; that each entry's test exists by spec file and name, and the document's shape, are NOTE lines (`../testing/fix-docs.js` fixes most).

- **Recurring bugs to look for.** Every migration found most of these:
  - `store.add()` used to apply an update (Akita skips ids already present, so edits never land; `upsert` is the fix).
  - `store.remove(undefined)` or `remove(null)` after a delete whose API returns 204 or whose SignalR payload is a bare id: Akita treats it as "remove all" and wipes the store.
  - `subscribe()` with no error callback (see above for when it is a bug).
  - A hub call or promise chain with no `.catch` (pin with `rejectInvokes` and `captureUnhandledRejections`).
  - Two stores with the same `@StoreConfig` name overwriting each other in the registry.
  - `getActiveId.toString()` or `canX` passed without calling it (a method reference compared to a value, always truthy).
  - `splice(-1, 1)` when an id isn't found (`indexOf` returned -1), removing the wrong item.
  - SignalR `onreconnected` rejoining only some groups, or no backoff after a failed `start()`.
  - Null dates turned into the 1970 epoch by a date-conversion helper.
  - A mutating control rendered with no permission read at all while the API requires a permission (an admin page gated only on a View permission, an Import button with no gate). The gates check cannot see it by design: there is nothing to inventory. Compare each mutating control with its endpoint's `[Authorize]`.
  - `ngOnDestroy` calling `unsubscribe()` on a `takeUntil` subject instead of `next()`: `takeUntil` never fires, so a polling `interval` keeps running after the page is gone, and the `complete()` that usually follows throws `ObjectUnsubscribedError` (vm.ui Recipe A).

## 4. What to test, in priority order

1. State-folder services (`state/` or `data/`): API result → store → query output, `loading` and error paths, and SignalR handlers that upsert or remove entities. Every state folder, not just the main one.
2. Permission and visibility gates in services and components. Every gated component, directive and guard, as `check-repo.js gates` lists them; a gate left untested is a blocker, not a follow-up.
3. Queries with non-trivial selectors and combined streams.
4. Components: rendering per state, interactions that emit outputs or call services, dialogs.
5. Pipes and pure helpers.

## 5. The broken-gate check

`verify.sh` cannot do this one. Pick a permission gate the specs claim to cover and break it **at the component's call site** (the `canEdit$` the component builds, or the condition in its template) so it always allows. Breaking it inside the permission service breaks every gate at once, and any spec failing proves nothing about this gate. `../testing/break-gate.sh` makes the edit (`--site <file>:<line> --replace <old> <new>`), runs the spec, confirms the gate's own denied tests fail, restores the file byte for byte and logs the result (../testing/README.md, "The broken-gate check"). A gate whose denied test still passes when broken is a blocker. When a component computes one gate at two sites (in `ngOnInit` and again in a template-driven `tap`), break each site in turn and record which tests fail for each and why (assertion or NG0100): change-detection order, not source order, decides which value the children see first, since Testing Library's single `detectChanges` evaluates a view's own bindings before the embedded views of its `@if` blocks. The writer runs it on every gate it covered and on each gate the reviewer names. The reviewer reads the log, and names an extra gate (call site `path:line`, the edit, the denied tests expected to fail) only when the selection is weak: a gate in scope whose credited specs changed has no run, or a gate computed at two sites had only one broken.

## 6. Review criteria beyond the rules above

What the reviewer asks of every spec in scope, in addition to sections 1 to 5:

- **What would have to break in production for this to fail?** Each of these is a tautology:
  - an assertion only on a mock (`toHaveBeenCalled`) where the rendered DOM, query output or emitted value was available;
  - a stub that returns X and a test that checks X came back through nothing;
  - an assertion on text a stubbed child would render (it renders nothing);
  - a store, query or state service stubbed where the real one would run, which hides the code under test.

  A tautology that a gate credit relies on is a blocker; otherwise a should-fix.
- **Is each denied case a near miss, through the UI?** `check-repo.js gates --list` names the test counted as each gated file's denied case and the denied test naming each gate; the check recognizes the shape, so read them: the grant is close to the required one (never empty), each gate has its own, the gated action is clicked rather than the method called, and the allowed render holds exactly the permission, not an everything-granted render.
- **Does every allow-list entry hold?** Its reason is something the harness cannot render (a browser API jsdom lacks, a runtime that cannot load); a reason the harness could meet is a blocker.
- **Did the check miss a permission read?** A gate in a shape the check's pattern table lacks goes to the proposals file (For the standard), with the file.
- **Does a hub test use the payload the API sends?** (section 2, "Hub payloads come from the API").
- **Is every defect entered once, only in the document, and pinned at its current behavior?** A named test that asserts the fixed behavior is a blocker (section 3).
